# SYS-110 플레이어 기동 시스템

## 0. 문서 계약

### 0.1 이 문서가 결정하는 것

본 문서는 플레이어 기체의 현재 Canonical 기동 모델을 정의한다.

이 문서가 소유하는 범위는 다음과 같다.

- Mouse, W/S, A/D/R/F, Alt, Shift 등 기동 입력의 의미
- SteeringReference, CameraView, BodyFacing의 관계
- ControlledVelocity, GravityVelocity, ResultVelocity의 관계
- 이동 Command 활성·해제와 속력 변화
- PropulsionAuthority와 Gravity Support
- TPV 카메라의 회전·이동·FOV 반응
- Combat/Cruise, High Authority, 추진익 표현의 채택 상태
- 충돌·피격이 기동 상태에 들어오는 책임 경계
- 현행 Prototype Baseline의 필수 회귀 검증

### 0.2 이 문서가 결정하지 않는 것

다음은 다른 문서 또는 후속 설계가 결정한다.

- 자동 타게팅 후보 선정과 무기별 Target Selection
- 장비별 공격 판정과 직사 First-hit 규칙
- Hit/Damage의 공통 권위와 Commit 순서
- 부스트 자원의 최종 소모량과 경제적 가치
- 군도 전장에서 Combat/Cruise를 선택하는 작전 규칙
- 렌더링 LOD의 공통 기술 구현
- 충돌·피격별 Damage 수치
- 최종 기체 모델·리깅·VFX 제작 방식

자동 타게팅과 직사 화기는 `SYS-120`, 세션 자원과 장비 경제는 `SYS-140`, 군도 이동·탐색의 작전 의미는 `SYS-160`이 소유한다.

### 0.3 규칙 상태

본 문서는 서로 다른 확정 수준을 섞지 않는다.

| 상태 | 의미 |
|---|---|
| Canonical Baseline | 직접 조작 검증을 거쳐 현재 플레이 감각의 기준으로 승인된 동작 |
| Adopted Direction | 프로젝트 방향으로 채택했지만 기능·수치가 아직 구현 또는 검증되지 않은 설계 |
| Open Decision | 채택 여부 또는 구체 규칙이 미확정인 항목 |
| Prototype Tuning | 현행 감각 재현과 회귀 확인에 사용하는 변경 가능한 수치 |

현재 구현 클래스와 필드 이름은 Baseline을 설명하는 참고이며, 동일한 플레이 계약을 유지한다면 내부 구현은 변경할 수 있다.

# 1. 시스템 요약

플레이어 기동은 물리 시뮬레이션의 완전한 재현보다 **입력에 즉각 반응하고, 3D 공간에서 방향·고도·진입각을 예측 가능하게 선택하는 고기동 메카 조작감**을 우선한다.

현재 Baseline은 다음 한 문장으로 요약한다.

> **마우스로 SteeringReference를 제어하고, WASDRF를 하나의 3D 이동 Command로 합성한다. Command가 활성화되면 제어 속도의 방향은 즉시 현재 명령을 따르고 속력은 유한하게 증가한다. 입력을 해제하면 마지막 제어 방향을 유지한 채 속력과 추진 권한이 점진적으로 감소하고, 중력 보정이 풀리며 활강·낙하 상태로 전환된다.**

운동과 시점은 다음 요소로 분리한다.

```text
CameraView
SteeringReference
BodyFacing
ControlledVelocity
GravityVelocity
```

이 요소들은 항상 같은 방향일 필요가 없다.

# 2. 목표 운동감

## 2.1 핵심 목표

플레이어가 느껴야 하는 운동 특성은 다음과 같다.

- 마우스와 이동 입력에 대한 반응이 즉각적이다.
- Body가 아직 목표 방향을 따라잡지 못해도 이동 Command는 지연되지 않는다.
- A/D/R/F가 기존 진행 방향 때문에 장시간 무시되지 않는다.
- 반대 방향 명령에서도 완전히 정지한 뒤 다시 가속하는 방식만을 강제하지 않는다.
- 복합 입력이 단일 축 입력보다 더 높은 가속도나 최대속력을 만들지 않는다.
- 입력 해제 후 진행 방향이 임의로 튀지 않고 자연스럽게 감속·활강한다.
- 프리룩 중에는 카메라 탐색이 이동 기준을 오염시키지 않는다.
- 카메라와 디버그 표현은 실제 운동 상태를 읽기 쉽게 만들되 운동 계산을 소유하지 않는다.

## 2.2 물리 재현보다 제어 계약을 우선한다

본 시스템은 자유 강체의 관성을 그대로 보존하는 비행 시뮬레이션을 목표로 하지 않는다.

`Rigidbody`는 충돌을 포함한 모든 외부 물리 결과를 자동으로 누적하는 유일한 운동 Source of Truth가 아니라, Flight Core가 계산한 결과를 Unity Physics와 Scene에 반영하는 실행 경계다.

따라서 다음은 의도된 특성이다.

- 활성 Command가 ControlledVelocity의 방향을 강하게 지배한다.
- 방향 재지정과 속력 변화는 서로 다른 시간 규칙을 사용할 수 있다.
- 입력 해제 시 완전한 등속 운동 대신 제어 속력이 감쇠할 수 있다.
- 외부 물리 변화는 명시적인 Gameplay 규칙 없이 지속 기동 상태로 자동 편입되지 않는다.

## 2.3 기동과 전투의 관계

전투의 핵심 판단은 직접 조준 자체보다 다음에 가깝다.

- 적과 장비에 맞는 거리 확보
- 고도 선택
- 공격 가능한 각도 확보
- 측면·후방 위협 회피
- 자동 타게팅이 유효하게 작동할 수 있는 공간 관계 형성

즉 **기동 자체가 전투 효율을 만드는 구조**를 목표로 한다.

자동 타게팅 규칙 자체는 `SYS-120`이 결정한다.

# 3. 입력 의미와 Control Frame

## 3.1 입력 정의

| 입력 | 현재 Canonical 의미 | 상태 |
|---|---|---|
| Mouse | SteeringReference 제어. 평상시 CameraView도 같은 방향 사용 | Baseline |
| W / S | SteeringForward 기준 전진 / 후진 Command | Baseline |
| A / D | Steering yaw 기준 좌 / 우 Command | Baseline |
| R / F | World Up 기준 상승 / 하강 Command | Baseline |
| Alt | SteeringReference를 고정하고 CameraView만 조작하는 Freelook | Baseline |
| Shift | Maneuver/High Authority 예약 입력 | Open Decision |
| 이동 입력 없음 | 마지막 ControlledDirection 유지, ControlledSpeed와 PropulsionAuthority 감쇠 | Baseline |

`Shift`는 현재 입력과 Telemetry에는 존재하지만 Flight Motion을 변경하지 않는다. 구체 효과가 결정되기 전까지 플레이어에게 기능이 완성된 입력으로 안내하지 않는다.

## 3.2 Control Frame

입력축의 기준은 다음과 같다.

```text
W / S
→ SteeringForward / Backward

A / D
→ SteeringYaw Right / Left

R / F
→ World Up / Down
```

중요한 구분:

- `SteeringForward`는 실제 `BodyForward`가 아니다.
- A/D는 Pitch가 큰 상황에서도 안정적인 수평 좌우를 제공하기 위해 Steering yaw만 사용한다.
- R/F는 Body roll이나 Camera roll의 영향을 받지 않는 World Up을 사용한다.

## 3.3 통합 3D Command

현재 이동 Command는 개념적으로 다음과 같다.

```text
RawCommand
= SteeringForward × AxialInput
+ SteeringRight   × LateralInput
+ WorldUp         × VerticalInput
```

Command가 활성화되면 `RawCommand`를 정규화하여 `CommandDirection`으로 사용한다.

따라서:

- W, A, R은 동일한 Command 합성 단계에 참여한다.
- W+A 또는 W+A+R도 단일 축 입력과 같은 최대 제어 속력과 가속도를 사용한다.
- 각 축의 입력 크기는 Command 활성 여부와 방향 비율에 사용한다.
- 현행 Baseline은 활성화 threshold를 넘은 입력 크기를 별도 throttle 세기로 사용하지 않는다.

## 3.4 Dead Zone과 Hysteresis

각 축에는 Dead Zone을 적용한다.

RawCommand 활성 판정은 작은 입력 노이즈로 상태가 반복 전환되지 않도록 서로 다른 threshold를 사용한다.

```text
Inactive → Active
= ActivateThreshold 이상

Active → Inactive
= DeactivateThreshold 미만
```

`DeactivateThreshold`는 `ActivateThreshold`보다 크지 않아야 한다.

# 4. 운동 상태와 갱신 규칙

## 4.1 Canonical Motion State

현재 Flight Core는 다음 운동 상태를 명시적으로 구분한다.

```text
ControlledVelocity
= ControlledDirection × ControlledSpeed

ResultVelocity
= ControlledVelocity + GravityVelocity
```

각 상태의 의미:

| 상태 | 의미 |
|---|---|
| ControlledDirection | 현재 또는 마지막 유효 이동 Command가 결정한 제어 방향 |
| ControlledSpeed | 추진 제어가 소유하는 속력 |
| ControlledVelocity | 방향과 속력으로 구성한 제어 운동 |
| GravityVelocity | 중력 미보정과 중력속도 회복이 소유하는 운동 |
| PropulsionAuthority | 현재 추진이 중력을 얼마나 보정할 수 있는지 나타내는 0~1 상태 |
| ResultVelocity | Rigidbody에 적용할 Controlled와 Gravity의 합 |

입력 축별 장기 Velocity contribution은 보존하지 않는다.

## 4.2 Command 활성 중

유효 이동 Command가 있는 FixedStep에서는 다음 규칙을 사용한다.

1. `ControlledDirection`을 현재 `CommandDirection`으로 설정한다.
2. `ControlledSpeed`를 가속도 한도 안에서 `MaxControlledSpeed`로 접근시킨다.
3. `PropulsionAuthority`를 완전한 추진 상태로 설정한다.
4. Gravity Support를 적용하고 누적된 GravityVelocity를 회복시킨다.

현재 Baseline에서 방향 재지정은 속력 가속도와 별개로 즉시 일어난다.

이 특성은 A→D, W→A, 복합 입력 변경에서 즉각적인 조작 반응을 만드는 핵심 계약이다.

## 4.3 Command 해제 중

유효 이동 Command가 없는 FixedStep에서는 다음 규칙을 사용한다.

1. 마지막 `ControlledDirection`을 유지한다.
2. `ControlledSpeed`를 `CoastDeceleration`에 따라 0으로 접근시킨다.
3. `PropulsionAuthority`를 설정된 해제율에 따라 0으로 접근시킨다.
4. 남은 Authority에 따라 Gravity Support가 점진적으로 감소한다.
5. Command가 없을 때는 누적 GravityVelocity를 0으로 되감지 않는다.

따라서 본 문서에서 `Coast`는 완전한 등속 관성 비행과 동의어가 아니다.

> **Coast는 새 이동 Command가 없고, 마지막 제어 방향을 유지한 채 추진 속력과 추진 권한이 감쇠하는 과도 상태다.**

## 4.4 Gravity Support

Gravity Support는 `PropulsionAuthority`로부터 평가한다.

```text
UnopposedGravity
= PhysicsGravity × GravityScale × (1 - Support)
```

Command가 활성화되고 Support가 존재할 때만 `GravityVelocity`를 0 방향으로 회복한다.

의도:

- 추진 중에는 중력을 적극적으로 보정한다.
- 입력 해제 직후에는 남은 추진 권한 때문에 곧바로 완전 낙하하지 않는다.
- Authority가 감소하면 Glide/Sink가 점진적으로 나타난다.
- 새 추진 Command는 이미 누적된 낙하 운동을 다시 회복할 수 있다.

## 4.5 Body Attitude

`BodyFacing`은 `SteeringReference`를 제한된 최대 각속도로 추종한다.

```text
SteeringReference
→ DesiredBodyFacing
→ RotateTowards
→ BodyFacing
```

현재 Baseline에서는:

- Body가 목표 방향을 따라잡지 못해도 이동 Command는 SteeringReference를 즉시 사용한다.
- Body의 회전 자체를 사용해 ControlledVelocity를 간접 회전시키지 않는다.
- Flight Controller가 Player Rigidbody rotation을 쓰는 유일한 기동 컴포넌트다.
- 제어 중 Rigidbody angular velocity는 제거할 수 있다.

## 4.6 Partial Release와 Retarget

예:

```text
W + A
→ A Release
→ W
```

다음 FixedStep에서 CommandDirection은 W 방향으로 다시 계산된다.

- 과거 A contribution을 찾아 제거하지 않는다.
- ControlledSpeed는 별도 속력 규칙을 따르므로 축 해제 자체로 0이 되지 않는다.
- ControlledDirection은 새 통합 Command를 즉시 반영한다.

A→D처럼 부호가 반전되는 입력도 동일하게 현재 입력 스냅샷으로 해결한다. Press 횟수나 입력 순서는 별도의 추진 보너스를 만들지 않는다.

## 4.7 최대속력

현재 Hard Cap은 `ControlledSpeed`의 상한으로 동작한다.

- Command 활성 중에도 상한 이상으로 속력을 증가시키지 않는다.
- 방향 재지정은 속력 상한과 독립적으로 계속 가능하다.
- GravityVelocity 때문에 `ResultVelocity`의 크기가 ControlledSpeed 상한을 넘을 수 있다.

따라서 `MaxControlledSpeed`는 전체 Rigidbody 결과 속도의 절대 상한이 아니다.

## 4.8 초기화와 속도 소유권

최초 Scene 진입에서는 기존 Rigidbody velocity를 ControlledVelocity로 간주할 수 있다.

Respawn, teleport, 상태 복구에서는 호출자가 ControlledVelocity와 GravityVelocity를 명시적으로 분리해 전달한다.

Disable→Enable만으로 실제 Rigidbody velocity 전체를 다시 ControlledVelocity로 분류하지 않는다.

# 5. 외부 물리와 Gameplay Impact

## 5.1 현재 Baseline

Flight Controller는 매 FixedStep에 자신이 소유한 `ResultVelocity`를 Rigidbody에 적용한다.

충돌, 다른 컴포넌트 또는 외부 Physics가 Rigidbody velocity를 변경하면 Flight Core의 예상값과 실제값 사이의 차이를 진단할 수 있다. 그러나 현재 Baseline은 이 차이를 자동으로 ControlledVelocity나 GravityVelocity에 흡수하지 않는다.

따라서 자연 Rigidbody 반응은 다음 Flight Step에서 지속 운동으로 보존된다고 보장하지 않는다.

## 5.2 Canonical 책임 경계

> **Gameplay상 보존해야 하는 충돌·피격·넉백 효과는 우연한 Rigidbody 잔여 속도에 의존하지 않고, 명시적인 기동 영향으로 Flight Core에 전달한다.**

현재 확정된 것은 이 책임 경계까지다.

다음은 Open Decision이다.

- 순간 속도 변경 여부
- 제한 시간 ImpactVelocity 채널 도입 여부
- 강제 변위 또는 위치 보정 여부
- 조작 권한 감소 또는 경직 여부
- 같은 Tick의 다중 Impact 합산·우선순위
- Host Authority 및 Replication 계약

공통 Hit/Damage 권위와 처리 순서는 `ARCH-100`이 소유한다. 공격별 Impact 발생 조건과 Flight Core 적용 방식이 구체화되면 관련 Canon의 인터페이스를 함께 갱신한다.

# 6. View, Freelook, Camera

## 6.1 세 방향 상태

현재 시점 시스템은 다음을 분리한다.

```text
CameraView
SteeringReference
BodyFacing
```

평상시:

```text
Mouse
→ SteeringReference 즉시 갱신
→ CameraView 동일 방향
→ BodyFacing은 유한한 각속도로 추종
```

## 6.2 Alt Freelook

Alt Freelook 중에는:

- SteeringReference를 고정한다.
- Mouse는 CameraView만 변경한다.
- 기존 이동 입력은 고정된 SteeringReference를 계속 사용한다.
- BodyFacing은 기존 SteeringReference를 계속 추종한다.

Alt를 해제하면:

- SteeringReference는 CameraView 쪽으로 순간 이동하지 않는다.
- CameraView가 설정된 최대 각속도로 SteeringReference에 복귀한다.
- 복귀 중 새 Mouse 입력은 SteeringReference를 계속 조작할 수 있다.

## 6.3 Camera Rotation과 Translation

현재 Camera는 View-first 원칙을 사용한다.

- Rotation은 CameraView를 즉시 반영한다.
- LookAt 또는 회전 SmoothDamp로 입력 반응을 늦추지 않는다.
- Translation은 Target Anchor를 늦게 따라가며 속도감을 만든다.
- Target의 screen-space 이탈이 커지면 Anchor follow를 빠르게 한다.
- teleport 거리 이상 차이가 나면 Anchor를 즉시 맞춘다.

## 6.4 FOV

현재 FOV는 Combat/Cruise 모드가 아니라 Rigidbody의 실제 결과 속력으로 결정한다.

```text
ActualSpeed
→ 0~1 정규화
→ BaseFov + SpeedBonus
→ SmoothDamp
```

카메라 흔들림, roll, 순간 연출 FOV는 향후 Targeting의 논리 시야와 분리해야 한다.

# 7. Flight Phase와 Telemetry

현재 진단 계층은 다음 Phase를 사용한다.

| Phase | 현재 판정 의미 |
|---|---|
| Powered | 유효 이동 Command 활성 |
| Coast | Command 비활성이고 Gravity Support가 충분히 남은 과도 상태 |
| Glide | Command 비활성이고 Gravity Support가 낮아진 활강·낙하 상태 |

Phase는 현재 진단과 표현을 위한 분류다. 향후 Gameplay Mode와 동일한 것으로 간주하지 않는다.

Telemetry는 최소한 다음 정보를 관측할 수 있어야 한다.

- ControlledDirection / Speed / Velocity
- GravityVelocity
- ResultVelocity와 Rigidbody 실제 속도
- RawCommand와 CommandDirection
- PropulsionAuthority와 GravitySupport
- Camera / Steering / Body Forward
- Steering–Body, Steering–Motion, Body–Motion 각도
- Freelook / Camera recenter 상태
- 외부 속도 residual
- 예약 Maneuver 입력 상태

Diagnostics는 MotionState나 Solver를 직접 수정하지 않는다.

# 8. 향후 채택 방향

## 8.1 Combat / Cruise

Combat Mode와 Cruise Mode는 프로젝트의 채택된 상위 방향이지만 현재 Baseline에는 별도 Gameplay Mode 전환과 운동 차등이 구현되어 있지 않다.

향후에도 두 모드는 완전히 다른 물리 엔진보다 동일한 기본 Flight Core 위의 상위 상태로 구성하는 방향을 우선한다.

### Combat Mode

목표:

- 정밀 교전
- 딜각과 거리 조절
- 급선회·슬라이드·저고도 기동
- 화면/논리 시야 중심 Targeting

### Cruise Mode

목표:

- 섬 사이 장거리 이동
- 빠른 진입·이탈과 복귀
- 탐색과 항로 위협 대응
- 이동 방향 중심 Targeting

모드별 속도 상한, 가속도, 자세, FOV, 전환 방식은 구현·검증 전까지 Baseline 규칙이 아니다.

## 8.2 High Authority / Shift

Shift 입력은 향후 같은 Command의 제어 권한을 높이는 상태 후보다.

후보 효과:

- 가속도 증가
- 방향 제어 규칙 변경 또는 강화
- Gravity recovery 강화
- Body catch-up 강화
- 자원 소모

현행 Baseline에서는 어떤 효과도 확정하지 않는다.

## 8.3 대표 기동

| 기동 | 현재 위치 |
|---|---|
| 원형 기동 | 타겟 중심 선회와 거리 조절 후보 |
| 급선회 | 통합 Command Retarget으로 기본 감각 검증 가능 |
| 슬라이드·드리프트 | 표현 및 지상·저고도 규칙 미정 |
| 고공 이동 | 기본 상승은 가능, 비용·위험 규칙 미정 |
| 코브라형 급방향전환 | 연출·기능 후보 |

## 8.4 메카 자세와 추진익

TPV에서 기동 상태를 읽게 하는 후면 가독성은 채택 방향이다.

- 전투 자세와 순항 자세의 구분
- 골반 후방 쌍발 추진익
- 급선회 시 좌우 비대칭 표현
- 상승 시 하향 분사
- 고속 상태의 강한 후방 분사

현재 Scene의 Debug Thruster와 Vector Line은 운동 상태 검증 도구이며 최종 메카 아트의 구현 완료를 의미하지 않는다.

# 9. 다른 시스템과의 인터페이스

## 9.1 SYS-120 자동 타게팅·직사 화기

SYS-110은 다음 운동·시점 정보를 제공할 수 있다.

- Player position
- ResultVelocity와 필요 시 ControlledVelocity
- CameraView
- SteeringReference
- BodyFacing
- 현재 Flight Phase
- 향후 Combat/Cruise 상태

현재 Targeting은 구현 시 CameraView, SteeringReference, ResultVelocity 중 어떤 값을 공격 의도로 사용하는지 명시해야 한다.

향후 방향:

```text
Combat Mode
→ 논리 시야 중심 공격 의도

Cruise Mode
→ 이동 방향 또는 ResultVelocity 중심 공격 의도
```

Target Selection 자체는 SYS-110이 소유하지 않는다.

## 9.2 SYS-140 세션·장비·빌드·익스트랙션

SYS-140 또는 후속 밸런스가 결정할 수 있는 항목:

- High Authority의 자원 비용
- Cruise 지속 비용
- 고도 상승 비용
- 장비나 빌드가 Flight 튜닝값에 미치는 효과

현재 구현된 `Powered / Coast / Glide`, 속력, CommandActive, GravitySupport는 기동 연동 효과의 관측 후보지만, 실제 빌드 조건으로 아직 확정하지 않는다.

## 9.3 SYS-160 군도 작전·전방지원

SYS-160은 장거리 이동, 안전 항로, 위험 해역 진입, 탐색, 복귀의 작전 의미를 결정한다.

SYS-110은 해당 상황에서 실제 기체가 어떻게 움직이고 상태를 표현하는지를 소유한다.

별도 Cruise Mode가 구현되기 전에는 현재 Flight Baseline이 장거리 이동에도 동일하게 적용된다.

# 10. 필수 검증

## 10.1 Baseline 회귀 검증

### Test A — Mouse와 무입력 운동

이동 중 모든 Command를 해제하고 Mouse로 SteeringReference를 회전한다.

PASS:

- Body는 SteeringReference를 추종한다.
- ControlledDirection은 Mouse만으로 재지정되지 않는다.
- ControlledSpeed는 설정된 CoastDeceleration로 감소한다.
- Gravity Support는 PropulsionAuthority와 함께 감소한다.

### Test B — W Steering Command

Body와 SteeringReference가 다른 방향인 상태에서 W를 입력한다.

PASS:

- ControlledDirection은 BodyForward가 아니라 SteeringForward를 즉시 사용한다.
- Body는 별도의 제한 각속도로 SteeringReference를 추종한다.

### Test C — A → D Retarget

A 방향 이동 중 D로 입력을 반전한다.

PASS:

- 다음 FixedStep부터 D 방향이 ControlledDirection에 반영된다.
- 완전 정지 후 재가속을 강제하지 않는다.
- Press 횟수나 별도 transient timer가 결과를 바꾸지 않는다.

### Test D — 복합 입력 정규화

W, W+A, W+A+R을 동일한 초기 상태에서 유지한다.

PASS:

- Command 방향은 각 축 조합을 반영한다.
- 축 개수가 늘어도 목표 ControlledSpeed와 가속도가 증가하지 않는다.

### Test E — Partial Release

```text
W + A
→ A Release
→ W
```

PASS:

- 다음 FixedStep부터 ControlledDirection이 W 방향을 사용한다.
- A contribution을 삭제하는 별도 상태 조작이 없다.
- 축 해제 자체로 ControlledSpeed가 0이 되지 않는다.

### Test F — All Release

모든 이동 입력을 해제한다.

PASS:

- 마지막 ControlledDirection을 유지한다.
- ControlledSpeed가 CoastDeceleration에 따라 감소한다.
- PropulsionAuthority가 설정된 해제율에 따라 감소한다.
- Gravity Support가 점진적으로 풀리고 Glide로 전환된다.

### Test G — Gravity Recovery

GravityVelocity가 누적된 Glide 상태에서 새 이동 Command를 입력한다.

PASS:

- PropulsionAuthority가 회복된다.
- 새 미보정 중력이 감소한다.
- 기존 GravityVelocity가 설정된 회복 가속도 안에서 0으로 접근한다.

### Test H — Freelook

이동 중 Alt를 누르고 CameraView를 회전한 뒤 해제한다.

PASS:

- Alt Hold 중 SteeringReference와 이동 기준이 고정된다.
- Alt Release 시 CameraView만 SteeringReference로 복귀한다.
- 카메라 복귀가 ControlledDirection을 순간 변경하지 않는다.

### Test I — Body 추종

SteeringReference를 큰 각도로 빠르게 변경한다.

PASS:

- Body는 최대 회전속도 안에서 추종한다.
- 이동 Command는 Body catch-up을 기다리지 않는다.

### Test J — FOV와 Camera Translation

저속과 고속 이동, 큰 screen-space 이탈, teleport를 각각 재현한다.

PASS:

- FOV는 실제 Rigidbody 속력에 따라 보간된다.
- Camera rotation은 ViewState를 즉시 반영한다.
- Anchor translation만 완만하게 추종한다.
- 큰 이탈에서는 catch-up이 빨라지고 teleport에서는 snap한다.

### Test K — 외부 Rigidbody 변화

Flight Core 외부에서 Rigidbody velocity를 변경한다.

PASS:

- 예상 속도와 실제 속도의 차이를 진단할 수 있다.
- 명시적인 Flight State 적용이 없으면 외부 변화가 지속 운동으로 자동 편입되지 않는다.

### Test L — 예약 Maneuver 입력

Shift를 누른 상태와 누르지 않은 상태를 비교한다.

PASS:

- 현행 Baseline에서는 Flight Motion 결과가 달라지지 않는다.
- 입력 상태는 향후 검증을 위해 Telemetry로 관측할 수 있다.

## 10.2 향후 플레이 검증

다음은 Baseline 회귀 조건이 아니라 후속 설계 검증이다.

- 자동 사격과 결합했을 때 기동·포지셔닝 판단이 재미를 만드는가
- Combat/Cruise 구분이 실제 작전 판단과 조작 가독성을 개선하는가
- High Authority가 기본 기동을 무력화하지 않고 의미 있는 선택을 만드는가
- 충돌·피격 Impact가 조작감을 부당하게 빼앗지 않는가
- 실제 메카 자세와 추진익이 TPV에서 운동 상태를 명확히 전달하는가

# 12. Open Decisions

## 12.1 Combat / Cruise

- 전환 입력과 자동 전환 여부
- 모드별 속도·가속도 차이
- 모드별 Camera/FOV 차이
- 모드별 Targeting 문맥의 실제 계약
- 자세 전환 시간과 중간 상태

## 12.2 High Authority

- 실제 운동 효과
- 자원 비용
- 지속형·토글형·순간형 입력 여부
- Gravity Support와 Body turn에 미치는 영향

## 12.3 Gameplay Impact

- ImpactVelocity 채널 필요 여부
- 순간 변화와 지속 변화의 구분
- 다중 Impact 합산 규칙
- Damage/Hit Pipeline과 적용 순서
- Host Authority와 Replication

## 12.4 Camera와 표현

- 최종 메카 모델 기준 Camera distance
- 실제 Combat/Cruise FOV
- Camera collision 대응
- Camera shake와 Targeting 논리 시야의 분리
- 추진익 크기·위치·가동 범위

## 12.5 운동 확장

- Analog 입력에서 입력 크기를 throttle로 사용할지 여부
- Ground/Water proximity에 따른 별도 보정
- Gravity 방향이 World Down으로 고정되지 않는 지역의 지원 여부
- 장비·손상·빌드가 Flight 튜닝값에 미치는 범위

# 13. Canonical 요약

1. **현재 승인된 기동은 통합 3D Command 모델이다.** W/S, A/D, R/F를 각각 SteeringForward, SteeringRight, WorldUp 기준으로 합성한다.
2. **SteeringReference와 BodyFacing은 분리된다.** 이동은 SteeringReference를 즉시 사용하고 Body는 유한한 속도로 추종한다.
3. **방향과 속력은 다른 규칙을 사용한다.** 활성 Command는 ControlledDirection을 즉시 갱신하고 ControlledSpeed는 유한 가속도로 변한다.
4. **운동 소유권은 ControlledVelocity와 GravityVelocity로 분리된다.** ResultVelocity는 두 성분의 합이다.
5. **입력 해제는 등속 비행이 아니다.** 마지막 방향을 유지하면서 ControlledSpeed와 PropulsionAuthority가 감쇠하고 Gravity Support가 풀린다.
6. **프리룩은 조향과 카메라를 분리한다.** Alt Hold 중 CameraView 변화가 SteeringReference를 변경하지 않는다.
7. **Flight Core가 Rigidbody 결과를 소유한다.** 외부 물리 변화는 명시적 Gameplay 규칙 없이 지속 운동으로 자동 편입되지 않는다.
8. **충돌·피격의 운동 효과는 명시적으로 전달한다.** 구체 이벤트와 합산 규칙은 Open Decision이다.
9. **Combat/Cruise, High Authority, 실제 추진익 표현은 채택 방향 또는 Open Decision이다.** 현재 Baseline 구현 완료를 의미하지 않는다.
10. **Prototype 튜닝값은 회귀 기준이다.** 플레이 감각을 보존하면서 검증을 통해 변경할 수 있다.
