# SYS-110 플레이어 기동 시스템

## 0. 문서 계약

### 0.1 이 문서가 결정하는 것

본 문서는 플레이어 기체의 **현재 Canonical 기동 모델**을 정의한다.

이 문서가 소유하는 범위는 다음과 같다.

- Mouse, W/S, A/D/R/F, Shift 등 플레이어 기동 입력의 의미
- Facing, Velocity, Main Thrust의 관계
- Axial Controller와 Maneuver Controller의 책임
- Coast, Main-axis Capture, High Authority, Hard Speed Limit 등 운동 규칙
- 전투 기동 모드와 크루즈 모드의 기동 역할
- 기동 상태를 전달하는 TPV 카메라 반응
- 크루징 자세, 골반 후방 쌍발 추진익 등 기동 상태의 시각적 표현
- 운동 모델의 필수 검증 시나리오

### 0.2 이 문서가 결정하지 않는 것

다음은 다른 문서 또는 후속 설계가 결정한다.

- 자동 타게팅 후보 선정과 무기별 Target Selection
- 장비별 공격 판정과 직사 First-hit 규칙
- 부스트 자원의 최종 소모량과 경제적 가치
- 군도 전장에서 전투/크루즈 모드를 언제 선택하는지에 대한 작전 규칙
- 렌더링 LOD의 공통 기술 구현
- 최종 FOV 수치와 카메라 튜닝값
- 최종 제어 수식과 가속도·authority 계수
- Alt/Ctrl 기반 Facing–Main Thrust 분리 기능의 채택 여부

자동 타게팅과 직사 화기는 `SYS-120`, 세션 자원과 장비 경제는 `SYS-140`, 군도 이동·탐색의 작전 의미는 `SYS-160`이 소유한다.

### 0.3 과거 Prototype의 위치

Prototype 0~0.5의 진행 과정과 실패 원인은 현재 Canon 규칙이 아니다.

해당 내용은 다음 Archive 문서에서 관리한다.

- `90_Archive/Archive_SYS-110_Prototype_0x_운동모델_이력.md`

현재 기동 구현과 판단에서는 본 문서만 Canon으로 사용한다.

# 1. 시스템 요약

플레이어 기동은 **고기동 메카의 기민함을 유지하면서도 입력 의미와 관성을 예측 가능하게 만드는 것**을 목표로 한다.

핵심 조작은 다음 한 문장으로 요약한다.

> **마우스로 기수를 제어하고, W/S는 명확한 주추력축을 가진 지속 추진으로 사용하며, A/D/R/F는 현재 관성에 굴복하지 않는 고권한 기동 제어로 사용한다. 이동 입력이 해제되면 그 순간의 실제 Velocity를 그대로 관성으로 유지한다.**

운동 모델의 핵심은 다음 세 요소를 분리하는 것이다.

```text
Facing
Velocity
Thrust
```

세 요소는 항상 같은 방향일 필요가 없다.

그러나 플레이어에게 세 요소를 모두 독립 입력으로 직접 제어하게 하지 않고 다음 두 계층으로 단순화한다.

```text
W / S
= Main Propulsion / Power

A / D / R / F
= Maneuver Authority
```

모든 Controller는 하나의 실제 물리 상태를 변경한다.

```text
Rigidbody.linearVelocity
```

입력별 가상 Velocity contribution을 장기간 별도 상태로 보관하지 않는다.

# 2. 목표 운동감

## 2.1 핵심 목표

플레이어가 느껴야 하는 운동 특성은 다음과 같다.

- 기수 방향과 실제 이동 방향이 일시적으로 달라질 수 있다.
- 기수를 빠르게 돌려도 기존 Velocity가 자동으로 기수 방향으로 회전하지 않는다.
- A/D/R/F 입력은 기존 관성에 묻히지 않고 첫 FixedStep부터 유의미하게 반응한다.
- 반대 방향 기동에서도 완전히 정지한 뒤 다시 가속하는 것만을 강제하지 않는다.
- 이동 입력을 해제하면 기체는 현재 운동을 그대로 이어간다.
- 고기동은 강한 방향 제어를 제공하지만 무한한 속력 증가를 의미하지 않는다.
- 장거리 이동과 정밀 교전은 동일한 운동 모델 위에서 전투 기동 모드와 크루즈 모드로 역할을 구분한다.

## 2.2 Facing과 Velocity의 정확한 관계

단순한 표어로는 다음과 같이 표현할 수 있다.

```text
Facing != Velocity
```

다만 정확한 Canon은 다음과 같다.

> **Facing과 Velocity는 서로 독립된 상태이며, Body/View의 회전 자체는 Velocity를 직접 변경하지 않는다.**

금지되는 관계:

```text
Mouse 회전
→ Body 회전
→ Velocity 자동 회전
```

허용되는 관계:

```text
Mouse 회전
→ Facing 변경
→ W/S 또는 Maneuver 입력
→ 추진/FCS Control ΔV
→ Velocity 변화
```

## 2.3 관성의 역할

본 시스템에서 관성은 **입력 중 플레이어의 명령을 거부하는 장애물**보다 **입력을 해제한 뒤 남는 실제 운동**으로 느껴져야 한다.

따라서:

```text
입력 중
→ FCS가 현재 Command를 적극 수행

입력 해제
→ 현재 실제 Velocity를 그대로 Coast
```

를 기본 감각으로 사용한다.

## 2.4 기동과 전투의 관계

전투의 핵심 판단은 직접 조준 자체보다 다음에 가깝다.

- 적과 장비에 맞는 거리 확보
- 고도 선택
- 공격 가능한 각도 확보
- 측면·후방 위협 회피
- 자동 타게팅이 유효하게 작동할 수 있는 공간 관계 형성

즉 **기동 자체가 전투 효율을 만드는 구조**를 목표로 한다.

자동 타게팅 규칙 자체는 `SYS-120`이 결정한다.

# 3. 입력 의미와 Control Frame

## 3.1 입력 정의

| 입력 | Canonical 의미 |
|---|---|
| Mouse | 기수 / Facing 제어 |
| W | 실제 Body Forward 기준 전방 주추력 |
| S | 실제 Body Backward 기준 후방 주추력 |
| A / D | View-yaw 기준 좌우 고권한 기동 |
| R / F | World Up 기준 상하 고권한 기동 |
| Shift | 동일 Control Law의 High Authority |
| 이동 입력 없음 | 현재 Velocity 그대로 Coast |
| Alt 또는 Ctrl | Facing–Main Thrust 분리를 위한 후보 입력. 미확정 |

## 3.2 입력축은 동일한 3D 방향키가 아니다

W/S와 A/D/R/F를 하나의 Desired Direction에 단순 합산하는 구조를 기본으로 하지 않는다.

```text
W / S
= Power / Main Propulsion

A / D / R / F
= High-authority Maneuver
```

이 비대칭성이 전술기형 운동 모델의 핵심이다.

## 3.3 Control Frame

입력축의 기준은 다음과 같이 고정한다.

```text
W / S
→ Actual Body Forward / Backward

A / D
→ View Yaw Control Right / Left

R / F
→ World Up / Down
```

이 기준은 기체가 기울거나 기존 Velocity가 다른 방향을 향하더라도 입력 의미가 불필요하게 변하지 않도록 하기 위한 것이다.

# 4. 운동 모델

## 4.1 Single Physical Velocity

운동 상태의 기준은 가능한 한 하나로 유지한다.

```text
Rigidbody.linearVelocity
```

매 FixedStep에서 개념적으로 다음과 같이 계산한다.

```text
Current Velocity
+
Axial Control ΔV
+
Lateral / Vertical Control ΔV
=
Next Velocity
```

다음과 같은 입력별 장기 Velocity 상태를 기본 구조로 사용하지 않는다.

```text
PersistentVelocity
LateralContribution
VerticalContribution
RevectorCorrection
```

## 4.2 운동 상태의 불변조건

1. Orientation과 Velocity는 독립된 상태다.
2. Body/View 회전 자체는 Velocity를 바꾸지 않는다.
3. Translation 변화는 유한한 Control ΔV를 통해 발생한다.
4. 이동 입력이 없으면 Flight Controller는 translation ΔV를 만들지 않는다.
5. 입력 해제 순간 실제 Velocity에 discontinuity가 발생하지 않는다.
6. 동일 Current State + 동일 Current Command에서는 입력 순서가 Control Output을 바꾸지 않아야 한다.

## 4.3 Error-driven Control

고권한 기동은 KeyDown 이벤트나 고정 시간 Burst에서 발생하지 않는다.

```text
Current State
+
Current Command
→ Motion Error
→ Required Authority
```

현재 운동과 현재 Command의 오차가 크다면 입력을 오래 유지해도 높은 authority가 유지될 수 있다.

다음 방식은 Canon으로 사용하지 않는다.

```text
KeyDown
→ N초 동안 Revector bonus
```

또는:

```text
입력 후 0.16초 강한 제어
→ 이후 무조건 약한 제어
```

## 4.4 Command Order Independence

동일한:

```text
Current State
+
Current Command
```

라면 W를 먼저 눌렀는지 A를 먼저 눌렀는지 때문에 현재 Control Output이 달라져서는 안 된다.

필요한 과거 정보가 있다면 암묵적인 입력 순서가 아니라 명시적인 Controller State로 표현한다.

# 5. Controller 구조

## 5.1 전체 구조

권장 책임 구조는 다음과 같다.

```text
PlayerFlightController
    │
    ├─ Rigidbody Current Velocity
    │
    ├─ Attitude Controller
    │     └─ Mouse → Facing
    │
    ├─ Axial Controller
    │     └─ W / S
    │
    └─ Maneuver Controller
          └─ A / D / R / F
```

Controller들이 각자 장기적인 가상 Velocity를 소유하지 않는다.

## 5.2 Attitude Controller

기본 관계:

```text
Mouse
  ↓
Desired Facing
  ↓
Body / Nose
```

Body/Nose 회전은 그 자체로 Velocity를 변경하지 않는다.

기본 상태에서는 Main Thrust Reference가 Facing과 결합된다.

```text
Mouse
→ Facing
→ Main Thrust Reference
```

## 5.3 Axial Controller

Axial Controller는 W/S를 담당한다.

입력:

```text
Current Velocity
Body Forward
Axial Input
High Authority State
Current Maneuver Command
```

출력:

```text
Axial Control ΔV
```

책임:

1. Body Forward/Backward 방향의 주추력 생성
2. W/S가 유지될수록 주추력축이 장기 운동에서 강한 영향력을 갖도록 함
3. 현재 플레이어가 명령하지 않은 횡방향 drift를 점진적으로 회수
4. 현재 Maneuver Command가 요구하는 운동 성분을 임의로 제거하지 않음

### Main-axis Capture

W/S가 활성화된 동안 기존 비의도 관성이 영구적으로 남지 않도록 주추력/FCS가 운동을 점진적으로 주추력 방향으로 수렴시킨다.

```text
Uncommanded drift
→ Main/FCS가 회수

Commanded maneuver
→ 유지
```

따라서 W+A 상태에서 Axial Controller가 A의 의도된 횡기동을 즉시 제거해서는 안 된다.

## 5.4 Maneuver Controller

Maneuver Controller는 A/D/R/F를 담당한다.

입력:

```text
Current Velocity
Lateral Input
Vertical Input
View Control Frame
World Up
High Authority State
```

출력:

```text
Lateral / Vertical Control ΔV
```

책임:

- 기존 반대 방향 관성이 있어도 첫 FixedStep부터 유의미한 correction 발생
- 기존 반대 운동성분을 적극 상쇄
- 목표 방향 운동을 빠르게 생성
- KeyDown 횟수와 무관하게 현재 오차로 authority 결정
- Release 시 해당 축 Velocity를 0으로 만들지 않음
- 변경된 실제 Velocity를 Coast 상태로 그대로 남김

## 5.5 방향제어와 속력제어의 분리

고기동의 기민함과 무한한 속력 증가를 분리한다.

Control ΔV는 개념적으로 다음 두 성분으로 볼 수 있다.

```text
Normal Control
+
Tangential Control
```

### Normal Control

현재 Velocity에 대체로 수직인 제어다.

목표:

```text
속력 변화는 작게
방향 변화는 크게
```

A/D/R/F의 고권한 방향 전환에서 우선한다.

### Tangential Control

현재 Velocity와 같은 또는 반대 방향 성분이다.

목표:

```text
속력 증가 / 감소
```

주로 Main Propulsion과 속력 제어가 담당한다.

따라서 높은 Maneuver Authority 자체가 불필요한 속력 증가를 만들어서는 안 된다.

# 6. 기동 모드와 대표 기동

## 6.1 모드의 위치

전투 기동 모드와 크루즈 모드는 **서로 다른 물리 엔진을 사용하는 두 비행모드가 아니다.**

둘은 동일한 기본 운동 모델 위에서 플레이 목적, 허용되는 기동 강도, 카메라·정보 표현, 타게팅 문맥을 다르게 사용하는 상위 상태다.

현재 Canon에서 두 모드는 입력축의 기본 의미를 바꾸지 않는다.

## 6.2 전투 기동 모드

목적:

- 정밀 교전
- 딜각 확보
- 타겟 중심 거리 조절
- 급선회·슬라이드·드리프트 등 근거리/저고도 기동
- 장비 교체와 자동 사격을 활용한 전투

특징:

- 직립 또는 반직립 전투 자세를 기본 표현으로 사용
- 장거리 순항보다 기동성과 공간 조절을 우선
- SYS-120의 전투 모드 Targeting과 연결

`원형 기동`은 타겟 중심 선회와 거리 조절을 지원하는 대표 기동 후보이지만, 정확한 반자동 보조 방식은 본 문서에서 아직 확정하지 않는다.

## 6.3 크루즈 모드

목적:

- 장거리 이동
- 빠른 진입·이탈
- 탐색
- 복귀
- 고속 이동 중 공중 위협 대응

특징:

- 전방으로 눕는 순항 자세와 추진익 전개로 상태를 시각적으로 구분
- 정밀 지상 교전보다 이동·탐색을 우선
- SYS-120의 크루즈 모드 Targeting 문맥과 연결
- SYS-160의 군도 탐색·복귀 공간과 연결

크루즈 모드의 구체적인 속도 상한, 가속도, 전환 시간은 테스트값이며 현재 확정하지 않는다.

## 6.4 High Authority

Shift는 별도의 조작축이나 전혀 다른 Control Law가 아니다.

> **같은 명령을 더 높은 FCS/추진 권한으로 수행하는 상태**

이다.

변경 가능한 항목:

- 최대 기동 가속도
- 방향 전환 authority
- 반대 관성 상쇄 능력
- Body catch-up authority
- 필요 시 Main-axis Capture authority

변경하지 않는 항목:

- Command direction
- 입력축 의미
- W/S와 A/D/R/F의 역할

제안서에서 말하는 `부스트` 자원과 High Authority의 정확한 비용 연결은 아직 본 운동 모델에서 확정되지 않았다.

따라서 현재는 다음만 Canon으로 둔다.

```text
Shift / High Authority
= 운동 제어 권한 증가

부스트 자원 소모량
= SYS-140 및 후속 밸런스에서 확정
```

## 6.5 대표 기동의 위치

현재 프로젝트 기획에서 다음 기동을 후보로 사용한다.

| 기동 | 현재 역할 | 상태 |
|---|---|---|
| 원형 기동 | 타겟 중심 선회와 거리 조절 | 기능 방향 채택, 보조 방식 미정 |
| 급선회 | 측면·후방 위협 대응 | 채택 |
| 슬라이드·드리프트 | 지상·저고도 전투에서 측방 기동 표현 | 채택 방향, 세부 제어 미정 |
| 고공 이동 | 위험 회피와 공간 장악 | 채택 방향, 비용 미정 |
| 코브라형 급방향전환 | 고속 상태의 큰 방향 변경 | 연출·기능 후보, 제어법 미정 |

이 표는 운동 모델의 Controller 수식을 정의하지 않는다.

# 7. 경계 조건과 연속성

## 7.1 Low-speed

Velocity가 거의 0이면 Velocity direction을 이용한 오차 계산이 불안정하다.

따라서:

```text
High speed
→ Motion Error / Velocity Direction 기반 제어

Low speed
→ Command Direction Acceleration 중심 제어
```

로 자연스럽게 전환한다.

정지 상태의 입력이 특정 목표속도로 즉시 순간이동하는 방식은 사용하지 않는다.

## 7.2 180도 반전

고기동 기체는 반드시:

```text
→
0
←
```

순서로 완전 정지한 뒤 역방향 가속할 필요는 없다.

가능하면:

```text
→
↘
↓
↙
←
```

처럼 일부 속력을 유지하면서 Velocity direction을 회전할 수 있어야 한다.

정확히 180도일 때의 회전 평면은 결정론적으로 선택해야 한다.

후보:

- A ↔ D: View horizontal control plane
- R ↔ F: World vertical 관련 plane
- W ↔ S: 안정적인 fallback axis 필요

구체 수식은 Open Decision이다.

## 7.3 Hold와 반복 입력

다음 두 입력은 중간 No-input 구간 때문에 완전히 같을 필요는 없다.

```text
D Hold
```

```text
D - D - D - D
```

그러나 다음은 금지한다.

```text
KeyDown 횟수 증가
→ Revector bonus 증가
```

동일 Command의 재입력 자체가 추가적인 추진 에너지나 FCS authority를 충전해서는 안 된다.

## 7.4 Partial Release

예:

```text
W + A
→ A Release
→ W
```

A가 과거에 만든 가상 contribution을 찾아 제거하지 않는다.

현재 실제 Velocity를 기준으로 새 Command `W`에 맞는 제어를 다시 계산한다.

따라서 Release 순간 Velocity discontinuity가 발생하지 않는다.

## 7.5 All Release

모든 이동 입력이 해제되면:

```text
Axial Control = 0
Lateral Control = 0
Vertical Control = 0
```

이 된다.

그리고:

```text
Velocity before release
≈
Velocity after release
```

여야 한다.

이후 현재 Velocity로 Coast한다.

## 7.6 Hard Speed Limit

Hard Speed Limit은 운동 조작을 정의하는 주 시스템이 아니라 안전장치다.

최대 속력 상태에서도:

```text
Speed increase X
Direction change O
```

를 목표로 한다.

따라서 Hard Cap은 주로 Velocity 크기를 더 증가시키는 Tangential acceleration을 제한하고, speed-neutral한 Normal/Revector Control은 가능한 한 유지한다.

# 8. TPV 카메라와 기동 표현

## 8.1 표현의 목적

Third Person View는 직접 조준 난도를 높이기 위한 시점이 아니다.

목표:

- 속도감
- 3D 공간감
- 메카와의 일체감
- 전투/크루즈 상태 판독
- 실제 이동속도를 과도하게 올리지 않고도 고속감을 전달

카메라와 기체 애니메이션은 **운동 상태를 플레이어에게 읽히게 하는 표현 계층**으로 취급한다.

## 8.2 전투/크루즈 카메라 반응

전투 기동 모드에서는 전투 대상·위협 방향·장비 사거리 등 근거리 판단의 가독성을 우선한다.

크루즈 모드에서는 진행 방향·경로·큰 위험·자원 신호 등 장거리 이동 판단을 우선한다.

현재 기획에서 다음 경향을 사용한다.

```text
감속 / 파밍
→ 좁은 편의 FOV, 근거리 판독 우선

전투
→ 중간 FOV, 안정적인 전투 시야

크루즈
→ 넓은 FOV, 속도감과 진행 방향 강조

부스트 크루즈
→ 더 넓은 FOV + 스피드 표현

모드 전환 / 임팩트
→ 짧은 카메라 압축 또는 줌 반응
```

## 8.3 FOV 테스트 범위

다음 값은 **Prototype 검증용 범위이며 확정 Canon 상수가 아니다.**

| 상태 | 기존 제안 테스트 범위 |
|---|---:|
| 감속·파밍 | 70~80 |
| 전투 모드 | 80~90 |
| 크루즈 모드 | 90~105 |
| 부스트 크루즈 | 100~110 테스트 상한 |
| 전환·임팩트 | 65~70의 짧은 압축 연출 후보 |

원칙:

- FOV 변화는 보간한다.
- 극단값은 지속 상태보다 짧은 연출에 우선 사용한다.
- FOV 확대가 실제 운동속도와 판독성을 해치지 않는지 검증한다.

렌더링 LOD의 공통 기술 정책은 본 문서가 소유하지 않는다.

## 8.4 TPV 후면 가독성

플레이어가 가장 오래 보는 영역을 우선한다.

- 등
- 허리
- 골반 후방
- 다리
- 후방 추진 구조

따라서 정면 전시용 실루엣보다 **실제 플레이 시점에서 기동 상태가 읽히는 후면 가독성**을 중시한다.

## 8.5 골반 후방 쌍발 추진익

기동 상태를 전달하는 핵심 시각 요소로 골반 후방 좌우의 쌍발 추진익을 사용한다.

기본 방향:

- 대형 백팩 날개보다 낮은 위치
- 좌우 추진익이 각도 변화 가능
- 본체 팔·다리 실루엣을 과도하게 가리지 않음
- 추진 방향과 기동 상태를 TPV 후면에서 읽을 수 있음

| 기동 상태 | 추진익 표현 | 전달 정보 |
|---|---|---|
| 기본 이동 | 후방 정렬, 약한 분사 | 정상 이동 |
| High Authority / 고속 이동 | 추진익 수렴 또는 강한 후방 분사 | 강한 추진 |
| 급선회 | 좌우 비대칭 전개 | 방향 전환 |
| 드리프트 | 한쪽 보정 분사 | 측면 미끄러짐 |
| 상승 | 하향 분사와 각도 변화 | 상승 |
| 위협 회피 | 짧은 펄스·급격한 각도 변화 | 즉각적인 회피 입력 |

정확한 각도, 속도, 분사 크기는 표현 튜닝값으로 남긴다.

## 8.6 Combat / Cruise 자세

### 전투 기동 모드

- 직립 또는 반직립 자세
- 팔·다리 움직임 노출
- 장비 운용과 방향 변화 가독성 우선

### 크루즈 모드

- 기체가 전방으로 기울거나 눕는 순항 자세
- 골반 후방 추진익 전개
- 전신 재조립형 변형보다 자세 전환을 우선

목적은 완전히 다른 기체로 변신하는 것이 아니라 **기능 상태를 플레이어가 즉시 구분하게 만드는 것**이다.

## 8.7 파트 애니메이션 구현 방향

현재 Prototype 단계에서는 리깅/스킨 웨이트에 크게 의존하기보다 파트별 독립 Transform 제어를 우선 후보로 둔다.

후보 방식:

```text
대표 Pose
+
파트별 Transform 보간
+
파트별 보간 속도 차이
```

적용 예:

- 상체 기울기
- 다리 접힘
- 팔 위치
- 추진익 전개
- 좌우 추진익 비대칭 회전

이 방식은 현재 개발 범위를 줄이는 구현 후보이며, 최종 아트 파이프라인을 영구 고정하는 규칙은 아니다.

## 8.8 표현 제약

- 추진익이 TPV 시야를 과도하게 가리면 안 된다.
- 모드 차이는 자세만 바뀌는 장식이 아니라 기능 상태와 함께 읽혀야 한다.
- 특정 작품이나 실존 전투기의 실루엣·비례·마킹을 직접 복제하지 않는다.
- 전투기적 속도감과 추진 문법은 기능적 조형 원리로 재해석한다.

# 9. 다른 시스템과의 인터페이스

## 9.1 SYS-120 자동 타게팅·직사 화기

SYS-110은 다음 운동 정보를 제공한다.

- Player position
- Facing
- Velocity
- Combat / Cruise 상태
- 필요 시 집중 기동 또는 타겟 중심 기동 상태

SYS-120은 이 정보를 이용해 공격 의도를 해석한다.

특히:

```text
Combat Mode
→ 화면/시야 중심 공격 의도

Cruise Mode
→ 이동 방향/Velocity 중심 공격 의도
```

라는 관계를 사용한다.

Target Selection 자체는 SYS-110이 소유하지 않는다.

## 9.2 SYS-140 세션·장비·빌드·익스트랙션

SYS-110은 High Authority와 고속 기동의 **운동 의미**를 정의한다.

다음은 SYS-140 또는 후속 밸런스가 결정한다.

- 부스트 자원의 최대량
- High Authority의 자원 소모
- 크루즈 지속 비용
- 고도 상승 비용
- 장비나 빌드가 기동 성능에 미치는 수치적 효과

## 9.3 SYS-160 군도 작전·전방지원

SYS-160은 전투 모드와 크루즈 모드가 어떤 작전 상황에서 필요한지를 결정한다.

예:

- 섬 사이 장거리 이동
- 안전 항로 이동
- 위험 해역 진입
- 탐색
- 복귀

SYS-110은 그 상황에서 실제 기체가 어떻게 움직이고 상태를 표현하는지만 소유한다.

# 10. 필수 검증

## 10.1 Test A — Mouse only

초기:

```text
Velocity →
Facing →
```

Mouse로 Facing을 ↑로 변경한다.

PASS:

```text
Facing ↑
Velocity →
```

Body 회전만으로 Velocity가 변하지 않는다.

## 10.2 Test B — W Main-axis Capture

초기:

```text
Facing ↑
Velocity →
```

W Hold.

PASS:

```text
→
↗
↑ 방향 우세
```

기존 횡관성이 점진적으로 회수된다.

FAIL:

- 계속 →만 유지
- 한 FixedStep에 ↑로 Velocity snap

## 10.3 Test C — A Immediate Maneuver

초기:

```text
Velocity →
```

A 입력.

PASS:

- 첫 FixedStep부터 좌측 correction 발생
- 기존 관성 때문에 장시간 입력이 무시되지 않음
- Velocity를 target 값으로 즉시 overwrite하지 않음

## 10.4 Test D — A → D

A 방향으로 실제 운동 중 D 입력.

PASS:

- 첫 FixedStep부터 D 방향 correction 시작
- 임의의 고정 타이머 종료 때문에 authority가 사라지지 않음
- 기존 A 방향 운동에서 충분히 빠르게 탈출

## 10.5 Test E — Hold vs Repeated Press

동일 초기 상태에서 D Hold와 D 반복 입력을 비교한다.

PASS:

- KeyDown 횟수 자체가 추가 Burst를 만들지 않음
- 차이가 있다면 중간 No-input 구간 때문임

## 10.6 Test F — W + A

PASS:

- W Main Propulsion 유지
- A가 즉시 궤적을 좌측으로 변경
- Main-axis Capture가 A의 현재 Command를 즉시 제거하지 않음

## 10.7 Test G — Partial Release

```text
W + A
→ A Release
→ W
```

PASS:

- Release 순간 Velocity discontinuity 없음
- 현재 Velocity에서 W Control로 자연스럽게 재수렴
- 과거 A contribution 삭제 같은 별도 상태 조작 없음

## 10.8 Test H — All Release

기동 중 모든 이동 입력 해제.

PASS:

```text
Velocity_before ≈ Velocity_after
```

이후 Coast.

## 10.9 Test I — Hard Cap Steering

Hard Speed 상태에서 A/D/R/F 입력.

PASS:

- 속력은 상한을 넘지 않음
- 방향은 계속 변경 가능

## 10.10 Test J — Combat / Cruise 판독성

동일한 기본 조작축을 유지한 채 전투 모드와 크루즈 모드를 반복 전환한다.

PASS:

- 자세와 카메라 반응만으로 현재 모드를 빠르게 구분 가능
- 크루즈 자세가 조작축 의미를 혼란시키지 않음
- 전투 모드 복귀 시 카메라와 자세 변화가 조작 반응을 방해하지 않음

## 10.11 Test K — TPV 추진익 가독성

기본 이동, High Authority, 급선회, 드리프트, 상승 상황을 후면 카메라에서 관찰한다.

PASS:

- 추진익 움직임이 기동 상태와 일관됨
- 팔·다리와 핵심 전투 시야를 가리지 않음
- 과도한 파트 운동으로 입력 방향을 오해하지 않음

# 11. Open Decisions

다음 항목은 현재 Canon에서 방향만 정해졌거나 아직 확정되지 않았다.

## 11.1 Axial Controller 수식

- Main-axis Capture의 정확한 Control Law
- Uncommanded drift와 Commanded maneuver를 구분하는 방법
- W/S 추진력의 속력별 변화

## 11.2 Maneuver Controller 수식

- Velocity-error 계산 방식
- Normal/Tangential ΔV 분해 방식
- 반대 관성 상쇄 한계
- High Authority 배율

## 11.3 Low-speed / High-speed 전환

- 전환 threshold
- 보간 방식
- 저속에서 Direction Servo 비중 감소 방식

## 11.4 180도 반전

- 결정론적 회전 평면
- W↔S 반전 시 fallback axis

## 11.5 Hard Speed Limit

- Tangential acceleration 제한 방식
- Speed Cap 근처의 Steering Authority 보존 방식

## 11.6 Facing–Main Thrust 분리

Alt 또는 Ctrl 기반 고급 조작은 후보 상태다.

기본 아이디어:

```text
Modifier Hold
→ Mouse = Facing only
→ Main Thrust Reference 유지
```

해제 방식 후보:

1. Main Thrust Reference를 빠르게 Facing 방향으로 catch-up
2. 다음 W/S 입력 시 다시 Facing과 결합

현재는 빠른 catch-up이 유력 후보지만 확정하지 않는다.

## 11.7 Combat / Cruise 운동 차등

다음은 아직 수치가 확정되지 않았다.

- 모드별 속도 상한
- 모드별 acceleration
- 모드 전환 시간
- High Authority 허용 범위
- 고도 유지/상승 비용
- 크루즈 모드에서 지상 정밀 기동 제한 수준

## 11.8 카메라

- 기본 FOV
- Combat / Cruise / Boost FOV 최종값
- Camera distance
- Camera lag

# 12. Canonical 요약

본 시스템의 현재 기준은 다음과 같다.

1. **Facing과 Velocity는 독립 상태다.** 회전만으로 Velocity를 바꾸지 않는다.
2. **W/S는 기수 기준 주추력이다.** 장기적으로 비의도 drift를 회수하지만 현재 Maneuver Command를 제거하지 않는다.
3. **A/D/R/F는 고권한 기동이다.** 기존 관성에 묻히지 않지만 Velocity를 순간 교체하지 않는다.
4. **실제 운동 상태는 Rigidbody Velocity 하나를 기준으로 한다.** 입력별 장기 가상 Velocity contribution을 우선하지 않는다.
5. **Authority는 Error-driven이다.** KeyDown 횟수나 고정 transient timer가 추진력을 생성하지 않는다.
6. **입력 해제는 Coast다.** Release 순간 Velocity discontinuity가 없어야 한다.
7. **고기동은 방향제어와 속력 증가를 분리한다.** Hard Speed에서도 방향 변경은 가능해야 한다.
8. **전투/크루즈 모드는 같은 운동 모델 위의 상위 상태다.** 기본 입력축 의미를 바꾸지 않는다.
9. **TPV 카메라·자세·추진익은 운동 상태를 읽히게 하는 표현 계층이다.** 숫자와 애니메이션 파라미터는 검증을 통해 확정한다.
10. **Prototype 0.x의 실패 이력은 Archive이며 현재 구현 규칙으로 사용하지 않는다.**
