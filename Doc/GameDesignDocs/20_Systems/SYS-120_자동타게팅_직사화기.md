# SYS-120 자동 타게팅·직사 화기 시스템 요구사항 및 설계

> **`ARCH-100`이 제공한 Broadphase 후보 집합에 저비용 Eligibility와 공통 Feature 계산을 한 번 적용하고, 무기별 작은 후보 집합에서 안정적으로 Target을 배정한다. 기본 고속 직사 화기는 발사 순간 `MuzzleSnapshot → TargetAnchorSnapshot`의 단일 First-hit로 차폐와 피격 대상을 함께 결정하며, 실제 Projectile Entity를 생성하지 않는다.**

## 0. 문서 계약

### 0.1 이 문서가 결정하는 것

본 문서는 플레이어 무기의 자동 타게팅과 기본 고속 직사 연사 화기가 어떤 대상을 선택하고 언제 발사하며, 발사 순간의 사선 결과를 어떻게 해석하는지 정의한다. Logical View·Eligibility·Bounds·Target Assignment·Retention, Aim·Fire·First-hit·Occlusion, 표현에 필요한 논리 정보와 시스템 고유 비용을 소유한다.

### 0.2 이 문서가 결정하지 않는 것

프로젝트 목표는 [PRJ-000](../00_Project/PRJ-000_프로젝트_통합기획_기준서.md)이 소유한다. 후보 공급, Stable ID, Authority·Replication, 공통 Hit/Damage Commit, Buffer·Visual 정책은 [ARCH-100](../10_Architecture/ARCH-100_전투_적성객체_아키텍처.md)을 따른다. 기동·시점은 [SYS-110](SYS-110_플레이어_기동.md), Missile의 생성·Guidance·군집은 [SYS-130](SYS-130_미사일_이타노서커스.md), 장비 슬롯·획득·내구도·빌드는 [SYS-140](SYS-140_세션_장비_빌드_익스트랙션.md)이 결정한다.

고정 스텝의 실행, ECS Stage 등록·봉인·완료 기록과 Job 결과 소비 경계는 [ARCH-110](../10_Architecture/ARCH-110_공용_타이밍_실행_계약.md)을 따른다.

### 0.3 적용 대상

기본 경로는 고속 Hitscan 계열과 탄 비행 자체가 핵심이 아닌 직사 연사 화기, 최대 4개 동시 장착 무기에 적용한다. 저속·유도·곡사 Projectile이나 지속적인 관통·도탄 Simulation이 필요한 화기는 `ARCH-100`의 `World Projectile` 경로 또는 별도 시스템 설계를 사용한다.

## 1. 설계 목표와 비목표

### 1.1 설계 목표

본 시스템의 목표는 다음과 같다.

1. 대량 적성 객체 환경에서도 플레이어 무기의 Target Selection 비용을 제한한다.
2. 최대 4개의 무기가 서로 다른 Target을 선택하더라도 공통 계산을 반복하지 않는다.
3. 화면과 이동 의도를 Targeting 입력으로 사용하되 Camera Shake·연출 FOV 같은 시각 노이즈가 Gameplay 판정을 흔들지 않게 한다.
4. Target이 자주 교체되어 무기·팔 조준이 불안정하게 보이는 현상을 억제한다.
5. 기본 직사 화기에서 지속적인 Projectile Simulation을 제거하면서 발사 순간의 장애물 차단과 중간 Target 피격은 유지한다.
6. Gameplay 판정과 Tracer·Impact 같은 시각 표현을 분리한다.

### 1.2 핵심 비목표

본 시스템은 실제 Projectile이 제공하는 모든 물리적 사건을 복원하지 않는다.

의도적으로 보장하지 않는 것:

- 발사 이후 사선에 새로 진입한 Target의 피격
- 발사 이후 새로 진입한 장애물의 차단
- 탄 비행시간
- 탄 자체의 비행 중 요격
- 기본 직사 화기의 지속 Collision Simulation
- 일반 경로에서의 복잡한 도탄·관통

이 예외를 복원하기 위해 기본 직사 화기를 다시 World Projectile 경로로 되돌리지 않는다.

## 2. 플레이어 공격 의도

### 2.1 Targeting 입력은 렌더링 카메라와 분리한다

렌더링 카메라는 다음 요소의 영향을 받을 수 있다.

- 화면비와 해상도
- 사용자 FOV 옵션
- Camera Pullback
- Camera Shake
- Roll
- 연출용 보간

따라서 Gameplay Targeting은 별도의 `LogicalTargetingView`를 사용한다.

```text
LogicalTargetingView
{
    LogicalYaw
    LogicalPitch
    TargetingFOV_or_Cone
    TargetingAspect
}
```

`Camera Shake`, `Roll`, 순간적인 연출 FOV 변화는 기본 Targeting 판정에 반영하지 않는다.

### 2.2 전투 모드

전투 모드는 화면 또는 마우스로 제어하는 논리 시야 중심을 공격 의도의 기준으로 사용한다.

목표:

- 플레이어가 시야에 담은 대상 우선
- 정밀 교전과 딜각 확보
- 무기별 유효 공격 방향을 읽기 쉽게 유지

구체적인 플레이어 기체의 카메라·시점 상태는 `SYS-110`을 따른다.

### 2.3 크루즈 모드

크루즈 모드는 플레이어의 이동 방향 또는 속도 벡터를 기준으로 넓은 전방 공격 의도를 표현할 수 있다.

목표:

- 고속 이동 중 전방 항로 위협 견제
- 카메라를 측면·후방 탐색에 사용하더라도 진행 방향 공격 의도 유지

최종 전방 Cone / Capsule 폭과 길이는 `Open Decisions`에서 검증한다.

### 2.4 명시적 집중 Target

수동 Lock-on 또는 특정 기동에서 명시적으로 지정된 Target이 존재하는 경우 일반 점수식보다 우선할 수 있다.

이 규칙은 플레이어의 직접 의도가 자동 분산 Targeting보다 높은 우선순위를 갖도록 하기 위한 것이다.

### 2.5 기본 위협도 자동 판단은 사용하지 않는다

기본 자동 Targeting은 대상의 전술적 위협도를 시스템이 임의로 평가하여 우선순위에 더하지 않는다. 위험한 대상을 먼저 처리할지 여부는 기본적으로 플레이어의 시야·기동·집중 Target 선택에 남긴다.

장비별 `TargetType` Eligibility나 명시적인 특수 Targeting 정책은 별도 규칙으로 둘 수 있지만, 이를 일반적인 “위협도 점수”와 동일하게 취급하지 않는다.

## 3. Target 모델

### 3.1 Candidate Set 입력 계약

본 시스템은 월드 전체 Entity를 직접 순회하지 않는다.

입력은 `ARCH-100`의 Combat Target Infrastructure가 반환한 관련 후보 집합이다.

현재 P1-B 구현은 이 최종 후보 공급 계약을 구현한 것이 아니다. 검증용 통합 경로는 매 fixed step ECS 후보를 직접 평가하며, 이 경로의 범위와 한계는 ARCH-110에 기록한다. Broadphase 후보 공급과 평가 주기 분리는 별도 구현·측정 전까지 현재 Canon의 요구사항으로 유지한다.

```text
ARCH-100 Broadphase
→ Candidate Set
→ SYS-120 Eligibility / Selection
```

본 문서는 Spatial Cell, Spatial Hash, Missile Proxy 등 후보 공급 방식 자체를 재정의하지 않는다.

### 3.2 Targeting Anchor

Target Selection과 Aim에는 논리적인 Target Anchor를 사용한다.

Target Anchor는 렌더링 Pivot이나 Collider 중심과 반드시 같을 필요는 없다. 대형 적·함선·미사일 등 대상 유형에 따라 조준 의도에 적합한 위치를 제공할 수 있다.

본 문서는 Target Anchor의 생성 방식을 정의하지 않는다. 후보 객체가 Aim/Hit에 사용할 논리 Anchor를 제공한다는 입력 계약만 둔다.

### 3.3 Target Type

후보는 최소한 Target Selection에서 필요한 Target Type 정보를 제공해야 한다.

예:

- 일반 적
- 함선 / 대형 적
- 드론
- 미사일

Target Type은 무기별 Eligibility와 Target Score에 사용할 수 있지만, 본 문서에서 전체 게임의 Target Type taxonomy를 확정하지 않는다.

## 4. Eligibility와 Bounds

### 4.1 Targeting Bounds와 Hit Bounds를 분리한다

하나의 Bounds를 Target 선택과 실제 Hit 판정에 동시에 사용하지 않는다.

**Targeting Bounds**의 질문:

```text
이 대상을 자동 타게팅 후보로 고려해도 되는가?
```

특성:

- 실제 Hit Bounds보다 넓게 설정 가능
- 대형 적이 화면 가장자리에 일부 노출된 경우를 보정 가능
- 작은 미사일을 선택하기 쉽게 보정 가능

**Hit Bounds**의 질문:

```text
실제 발사 사선이 이 객체를 통과했는가?
```

특성:

- 실제 피격 감각에 맞춰 별도 정의
- Targeting Bounds보다 작거나 다를 수 있음
- 미사일 요격 등 특정 대상에는 의도적인 보정 가능

이 분리를 통해 자동 Targeting의 편의 보정이 실제 피격 판정까지 과도하게 확대되는 것을 방지한다.

### 4.2 Cheap Eligibility

Broadphase 후보에는 먼저 저비용 조건만 적용한다.

```text
Targetable?
↓
Weapon Max Range 이내?
↓
Logical Targeting View 안?
↓
Weapon Type 정책상 유효?
```

기본 Eligibility 단계에서는 다음 고비용 처리를 수행하지 않는다.

- Physics LoS Query
- 미래 위치 정밀 예측
- 복잡한 탄도 계산
- 약점 탐색
- 고비용 Cluster 분석
- 정밀 유도 Solver

실제 고비용 Solver가 필요한 특수 무기는 별도의 정책을 둔다.

### 4.3 기본 직사 화기의 LoS 원칙

기본 고속 직사 연사에서는 Targeting 단계에서 별도 LoS Raycast를 기본 수행하지 않는다.

```text
Targeting
→ View + Range + Weapon Policy

Fire
→ First-hit Resolve
```

따라서 동일 Shot에 대해 Targeting LoS와 Hit Detection을 중복 수행하지 않는다.

## 5. Shared Target Feature

### 5.1 목적

최대 4개의 무기가 동일 후보를 평가할 때 공통 계산을 반복하지 않는다.

Eligibility를 통과한 Candidate마다 공통 Feature를 한 번 계산한다.

```text
SharedTargetFeature
{
    StableHandle
    LogicalScreenX
    LogicalScreenY
    DistanceSq
    TargetType
    CurrentTargetFlags
}
```

구체 필드는 구현 과정에서 조정할 수 있지만, **공통 Feature를 무기별로 반복 계산하지 않는 것**이 설계 원칙이다.

### 5.2 공통 계산 후보

- World → Logical Targeting View 변환
- DistanceSq
- Target Type
- 현재 Target 여부
- 공통 Target 상태 Flag

무기별 사거리, Mount Bias, 무기별 정책은 이후 Weapon Selection 단계에서 적용한다.

## 6. 최대 4개 무기 Target Selection

### 6.1 기본 원칙

- 동시에 평가하는 무기 수는 최대 4개를 기본 상정한다.
- Candidate의 공통 Feature는 1회 계산한다.
- 각 무기는 작은 고정 크기 후보 집합만 유지한다.
- 왼쪽 장착 무기는 왼쪽 후보를, 오른쪽 장착 무기는 오른쪽 후보를 선호할 수 있다.
- 후보가 하나뿐이면 모든 무기가 같은 Target을 선택할 수 있다.
- 후보가 충분하면 서로 다른 Target으로 분산하는 것을 우선할 수 있다.
- 플레이어가 명시한 집중 Target이 있으면 일반 분산 규칙보다 우선할 수 있다.

최종 장비 슬롯 구조는 `SYS-140`이 소유한다. 본 문서는 Target Selection 단계에서 최대 4개 무기 입력을 처리할 수 있는 구조를 정의한다.

### 6.2 전체 Candidate List 재저장 금지

Broadphase 이후의 모든 Valid Candidate를 별도 가변 List에 저장한 뒤 무기별로 다시 전체 순회하는 것을 기본 경로로 하지 않는다.

한 번의 Candidate 순회에서 각 무기의 작은 Top-M을 갱신한다.

```text
for each Candidate
{
    SharedTargetFeature 계산

    Weapon_0 Top-M 갱신
    Weapon_1 Top-M 갱신
    Weapon_2 Top-M 갱신
    Weapon_3 Top-M 갱신
}
```

Top-M 크기는 고정된 작은 값으로 두고 최종 수치는 프로파일링과 플레이 테스트 후 확정한다.

### 6.3 Weapon Score

초기 Score 구조는 다음 수준의 단순한 조합을 기본으로 한다.

```text
WeaponScore =
    SharedBaseScore
  + MountSideBias
  + CurrentTargetRetentionBias
```

`SharedBaseScore`의 정확한 구성과 가중치는 현재 확정하지 않는다. 기존 설계가 명시적으로 유지하는 구조는 `SharedBaseScore + MountSideBias + CurrentTargetRetentionBias` 수준의 단순 조합이다.

전역 최적 조합을 찾는 복잡한 Assignment Solver는 기본 경로에 사용하지 않는다.

### 6.4 Stable Assignment

무기별 Top-M이 완성된 뒤 Target을 결정한다.

기본 규칙:

1. `CurrentTarget`이 여전히 Valid하면 유지 우선.
2. Stable Weapon Order로 순차 할당.
3. 아직 선택되지 않은 유효 Target이 있으면 분산 우선.
4. 모든 유효 Target이 한 번 이상 선택되었거나 후보가 부족하면 중복 허용.
5. 동일 Score의 최종 tie-break는 Stable Handle을 사용.

예:

```text
Target 1개
→ W1 W2 W3 W4 모두 A 가능

Target 2개
→ 우선 A / B 분산
→ 나머지 무기는 각자의 상위 후보에 중복 가능

Target 4개 이상
→ 조건이 허용하면 최대 4개 서로 다른 Target 선택 가능
```

Gameplay 결과를 확정하는 권위와 Stable Commit 규칙은 `ARCH-100`을 따른다.

## 7. Target Retention / Hysteresis

### 7.1 목적

화면 중심 Score만으로 Target을 매 평가마다 다시 선택하면 작은 카메라 이동이나 후보 위치 변화에도 Target이 계속 바뀔 수 있다.

이는 다음 문제를 만든다.

- 메카 팔과 무기 방향의 시각적 흔들림
- 공격 대상의 예측 불가능성
- 반복 Target 계산 증가

따라서 현재 Target이 계속 유효하면 일정 우선권을 부여한다.

```text
CurrentTarget valid
→ 유지 우선

NewTarget score가 교체 기준을 충분히 초과
→ 교체 허용
```

### 7.2 교체 기준

최종 Hysteresis 수치와 유지 시간은 미정이다.

검증할 대상:

- Score 차이 기반 교체
- 최소 유지 Tick
- Target Type 변화 시 예외
- 수동 집중 Target 입력 시 즉시 교체

## 8. Fire / Aim

### 8.1 Aim

Target이 확정되면 무기 또는 장착부는 Target Anchor 방향으로 Aim한다.

플레이어 기체 자세·팔·장착부의 실제 움직임은 관련 animation / motion 구현과 연결될 수 있으나, 본 문서는 발사 가능 상태의 논리 조건만 정의한다.

### 8.2 Fire Alignment

발사 허용 여부에는 총구 방향과 Target 방향의 정합성을 사용할 수 있다.

```text
toTarget = TargetAnchor - MuzzlePosition
alignment = dot(MuzzleForward, normalize(toTarget))

alignment >= FireTolerance
→ Fire 가능
```

이 값은 Hit 판정이 아니라 **현재 무기가 실제로 Target 방향을 향하고 있는가**를 확인하는 Fire-control 조건이다.

최종 `FireTolerance`은 무기 특성과 플레이 테스트에 따라 결정한다.

### 8.3 Muzzle / Target Snapshot

Instant Resolve 직사 공격은 발사 순간 다음 정보를 Snapshot으로 고정한다.

```text
MuzzleSnapshot
TargetHandle
TargetAnchorSnapshot
WeaponHandle
CombatTick
```

발사 이후 Target이나 장애물이 이동해도 해당 Shot의 논리 사선은 다시 추적하지 않는다.

## 9. First-hit와 Occlusion

### 9.1 Direct-fire First-hit 계약

기본 직사 화기는 발사 시 `MuzzleSnapshot → TargetAnchorSnapshot` 구간을 한 번 Resolve한다.

```text
MuzzleSnapshot
→ TargetAnchorSnapshot
→ Segment Query
→ Nearest Valid Hit
→ SYS-120 Hit Classification
```

Physics query의 할당 정책, Buffer 재사용, 반환 순서 비신뢰, Stable tie-break와 권위 Commit은 `ARCH-100`을 따른다.

본 문서는 **첫 번째 유효 교차 대상을 어떤 Gameplay 의미로 해석할지**를 소유한다.

### 9.2 Intended Target

```text
First Valid Hit == Current Target
→ Intended Target Hit
```

이 경우 Target에 대한 Hit 결과를 생성한다.

실제 Damage Commit은 `ARCH-100`의 Hit / Damage Pipeline을 따른다.

### 9.3 Targetable Interceptor

현재 Target 앞에 다른 Targetable 객체가 존재하면 그 객체가 실제 피격 대상이 될 수 있다.

```text
Muzzle
→ Targetable B
→ Intended Target A
```

결과:

```text
B = Hit
A = 이번 Shot에서는 Hit 아님
```

중간 Targetable 객체에 맞았다는 이유만으로 Intended Target을 Occluded 상태로 만들지 않는다.

이 규칙을 통해 발사 순간 사선에 존재하는 적이나 요격 가능한 미사일이 중간에서 맞을 수 있다.

### 9.4 Blocking Geometry

Targetable이 아닌 Blocking Geometry가 먼저 교차하면 Shot은 차단된다.

```text
Muzzle
→ Wall / Terrain / Blocking Geometry
→ Intended Target
```

결과:

- Damage 없음
- 현재 Target에 짧은 Occlusion 상태를 부여할 수 있음

### 9.5 Occlusion Cache

복잡한 지속 차폐 Tracking을 만들지 않는다.

```text
OccludedTarget
{
    StableHandle
    ExpireTargetTick
}
```

Blocking Geometry에 의해 Shot이 차단된 경우 일정 기간 해당 Target의 선택 우선도를 낮추거나 후보에서 제외할 수 있다.

만료 후에는 정상 평가로 복귀한다.

최종 유지 Tick은 Open Decision이다.

## 10. 고연사 직사 화기 단순화

### 10.1 Instant Resolve를 기본으로 한다

탄 비행 자체가 핵심이 아닌 기본 고연사 직사 화기는 `ARCH-100`의 `Instant Resolve` 공격 모델을 사용한다.

```text
Target Selection
→ Aim / Fire
→ First-hit Resolve
→ Authoritative Hit Event
→ Damage Commit
→ Visual Event
```

실제 Projectile Entity의 Spawn·Movement·Lifetime·Collision 관리 비용을 만들지 않는다.

### 10.2 유지하는 Gameplay 특성

Instant Resolve에서도 다음을 유지한다.

| 기능 | 기본 직사 화기 |
|---|---|
| Intended Target 공격 | 유지 |
| 발사 순간 중간 Targetable 피격 | 유지 |
| 발사 순간 미사일 요격 | 유지 가능 |
| 발사 순간 장애물 차단 | 유지 |
| 최대 4무기의 서로 다른 Target 공격 | 유지 |
| Target Retention | 유지 |
| 화면/모드 기반 자동 Targeting | 유지 |
| 시각적 Tracer | 유지하되 Gameplay Projectile과 분리 |

### 10.3 의도적으로 포기하는 특성

| 기능 | 처리 |
|---|---|
| 발사 후 사선 진입 Target | 미반영 |
| 발사 후 장애물 진입 | 미반영 |
| 실제 탄 비행시간 | 제거 |
| 비행 중 지속 Collision | 제거 |
| 탄별 Network 동기화 | 기본적으로 없음 |
| 지속 Projectile 요격 | 해당 무기가 World Projectile 경로가 아니면 없음 |

특정 무기가 이러한 특성을 필요로 하면 기본 직사 경로가 아니라 별도 World Projectile 경로를 사용한다.

### 10.4 별도 Targeting Budget을 기본 요구하지 않는다

본 시스템의 기본 Targeting은 Broadphase 이후 저비용 Eligibility와 작은 Top-M 갱신을 전제로 한다.

따라서 기본 직사 화기를 위해 별도의 고비용 Targeting Budget을 먼저 도입하지 않는다.

향후 다음과 같은 실제 고비용 Solver가 추가될 때만 별도 처리 상한을 검토한다.

- 복잡한 미래 위치 예측
- 정밀 약점 탐색
- 고비용 Cluster 분석
- 복잡한 탄도 Solver
- 유도 Solver

공통 Combat Execution Budget은 `ARCH-100`이 소유한다.

## 11. 장비 인터페이스

### 11.1 SYS-140이 제공하는 정보

장비 시스템은 Targeting에 최소한 다음 정보를 제공해야 한다.

- 장비 Stable Handle 또는 동등 식별자
- 장착 위치 / Mount Side 정보
- Max Range
- 공격 방식
- Target 가능 Type / 정책
- FireTolerance 후보값
- 필요 시 Weapon-specific Target Bias

장비 획득, 슬롯 구성, 내구도, 소모품, 빌드 강화는 `SYS-140`이 소유한다.

### 11.2 공격 유형과 Targeting

장비 공격 방식은 Target Selection에서 서로 다른 Eligibility 또는 Bias를 요구할 수 있다.

예:

| 공격 방식 | SYS-120에서 필요한 Targeting 차이 |
|---|---|
| 고속 Hitscan / 직사 | 기본 Instant Resolve 경로 |
| 폭발형 Instant Attack | 착탄점 / 범위 Target 정책 필요 가능 |
| 유도형 | 기본 SYS-120 Selection 이후 별도 유도 시스템으로 전달 가능 |
| 곡사 / 저속 Projectile | 별도 탄도·World Projectile 설계 필요 |

본 문서는 모든 장비군의 상세 공격 Solver를 정의하지 않는다.

### 11.3 Missile Targeting

미사일이 플레이어의 Targetable 객체로 들어오는 경우, 후보 공급은 `ARCH-100`의 Target Infrastructure를 사용한다.

미사일의 생성·FSM·Guidance·HP·연출·군집 동작은 `SYS-130`이 소유한다.

SYS-120은 해당 미사일을 **플레이어 무기의 Target 후보로 선택하고, 발사 순간 First-hit 결과로 요격할 수 있는 규칙**만 소유한다.

## 12. 연출 요구사항

### 12.1 원칙

Gameplay 판정과 시각 표현을 분리한다.

SYS-120은 **어떤 Shot/Hit 정보가 표현에 필요한지**를 정의하고, Visual State Buffer·GraphicsBuffer·GPU VFX 등의 전송·렌더링 구조는 `ARCH-100`이 소유한다.

### 12.2 Tracer

Tracer는 실제 Gameplay Projectile이 아니다.

논리 판정:

```text
MuzzleSnapshot
→ TargetAnchorSnapshot
→ First-hit
```

시각 표현은 필요에 따라 Muzzle보다 앞쪽에서 시작할 수 있다.

```text
VisualStart =
Muzzle
+ (HitPosition - Muzzle) * TracerStartRatio
```

이 경우에도 실제 Hit Query는 반드시 Muzzle부터 시작한다.

`TracerStartRatio`는 연출 파라미터이며 Gameplay 판정에 영향을 주지 않는다.

### 12.3 Impact 정보

직사 화기 Hit 연출에는 최소한 다음 의미 정보가 필요할 수 있다.

```text
HitPosition
HitNormal
SurfaceType
WeaponVisualType
Seed
```

`SurfaceType` 후보:

- Armor
- Missile
- Barrier
- Terrain
- Static Structure

이 정보의 Buffer layout과 GPU 전달 방식은 ARCH-100이 결정한다.

### 12.4 Muzzle VFX

Muzzle Flash는 장착 무기 Transform과 강하게 연결되고 수량도 제한적이므로, 반드시 대량 GPU VFX 경로에 포함할 필요는 없다.

본 문서는 다음 요구만 둔다.

- Fire 논리 시점과 시각적 발사 피드백이 일치할 것
- Muzzle Flash 구현 방식이 Targeting/Hit 판정에 영향을 주지 않을 것

구현 방식은 Architecture의 공통 Visual 원칙 아래에서 선택한다.

## 13. 성능 요구사항

월드 Target 수를 `N`, Broadphase 이후 후보 수를 `M`이라 하면 SYS-120은 `N`이 아니라 `M`을 처리한다. 실제 개선 정도는 `ARCH-100`의 지표와 함께 프로파일링한다.

| 비용 원인 | 제한 규칙 | 줄어드는 비용 | 감수하는 대가·한계 |
|---|---|---|---|
| 월드 전체 Target 탐색 | `ARCH-100` Broadphase가 Candidate `M`만 공급 | SYS-120의 평가 대상을 `N`에서 `M`으로 제한 | Broadphase 품질과 갱신 비용은 ARCH 책임 |
| 최대 4개 무기의 반복 평가 | Candidate를 한 번 순회하고 Shared Feature와 작은 Top-M을 갱신 | 화면 변환·거리 계산·후보 복사를 무기마다 반복하지 않음 | 전역 최적 Assignment 대신 Stable 순차 할당 사용 |
| Targeting LoS와 Hit Query 중복 | Targeting은 Cheap Eligibility만 수행하고 발사 때 한 번 First-hit Resolve | Candidate별 Physics Query와 동일 Shot의 중복 판정 제거 | 장애물 차단은 실제 발사 시점에 확정 |
| 고연사 Projectile 생명주기 | 기본 직사는 Instant Resolve 사용 | Spawn·Movement·Lifetime·Collision과 탄별 Network 비용 제거 | 발사 이후 새로 생긴 교차·차단과 비행시간은 반영하지 않음 |

기본 경로에는 Candidate별 정밀 예측·약점 탐색·복잡한 조합 탐색이나 가변 Target List를 넣지 않는다. 이러한 Solver가 실제로 추가될 때만 별도 Budget을 검토한다. Buffer 재사용, Stable tie-break, Host Hit 권위와 Damage Commit 등 공통 Hot-path 정책은 `ARCH-100`을 따른다.

---

## 14. 현재 구현 상태

P1-B는 ARCH-110의 ECS Stage 안에서 후보 평가와 결과 Resolve/Commit의 실행 계약을 검증했다. 현재 경로는 `CombatTargetCandidate`를 매 fixed step 수집하여 평가하고, `ViewDot`·`DistanceSq`·`StableId` 순으로 동률을 해소한다.

이는 ARCH-100 Broadphase가 제공한 후보 집합, 최대 4개 무기의 Top-M 배정, Hitscan First-hit와 Damage Commit 전체를 구현한 것이 아니다. 자동 타게팅 활성 세션의 별도 CPU·GC 비용도 아직 측정하지 않았다. 검증 근거와 실행 한계는 [ARCH-110](../10_Architecture/ARCH-110_공용_타이밍_실행_계약.md) §9를 따른다.

## 15. 검증

아래 항목은 검증 질문이며 완료된 테스트 결과를 뜻하지 않는다.

### 15.1 Targeting 검증

- `LogicalTargetingView`가 렌더 카메라 Shake·Roll·연출 FOV에 의해 불필요하게 흔들리지 않는가?
- Targeting Bounds가 화면 가장자리의 큰 Target을 자연스럽게 포함하는가?
- 작은 Missile의 Targeting Bounds와 Hit Bounds 차이가 불공정하게 느껴지지 않는가?
- Target Retention으로 무기/팔 움직임과 공격 대상이 충분히 안정되는가?
- 좌/우 Mount Bias가 자연스러운 분산 사격을 만드는가?
- Target 수가 적을 때 중복 Targeting이 자연스럽게 작동하는가?
- Target 수가 충분할 때 최대 4개 무기가 의미 있게 분산되는가?

### 15.2 Fire / Hit 검증

- FireTolerance가 지나치게 느슨하거나 엄격하지 않은가?
- Intended Target 앞에 다른 Enemy/Missile이 있을 때 First-hit가 자연스럽게 느껴지는가?
- Static Geometry 차단 후 Occlusion Cache가 Target 흔들림을 줄이는가?
- 중간 Targetable 피격을 Occlusion으로 오인하지 않는가?
- 발사 후 개체 이동을 무시하는 Instant Resolve 근사가 실제 플레이에서 거슬리는가?
- First-hit 경로가 고연사 상태에서 CPU 병목이 되지 않는가?

### 15.3 멀티플레이/결정론 검증

공통 Authority 구현은 `ARCH-100`의 검증을 따르며, SYS-120에서는 다음 결과를 확인한다.

- 동일 입력에서 Stable Target Assignment가 재현되는가?
- 동일 Score 후보의 tie-break가 Stable Handle 기준으로 흔들리지 않는가?
- Host가 확정한 Hit Result와 Client의 시각 재생이 모순되지 않는가?
- 여러 무기가 같은 Target을 같은 Tick에 공격해도 SYS-120 Targeting 결과와 ARCH-100 Damage Commit 경계가 혼동되지 않는가?

### 15.4 연출 검증

- Tracer를 Gameplay Projectile 없이 표시해도 발사 방향을 자연스럽게 인지할 수 있는가?
- `TracerStartRatio`를 사용해도 총구에서 발사된 것으로 인지되는가?
- Muzzle / Tracer / Impact의 시각 타이밍이 논리 Shot과 충분히 일치하는가?
- 대량 Shot 시 시각 표현이 Gameplay Targeting 성능에 영향을 주지 않는가?

### 15.5 Profiling 항목

SYS-120에서 우선 수집할 지표:

- Broadphase 이후 전달받은 Candidate 수 평균 / 최대
- Cheap Eligibility 통과 수
- Candidate 1회 순회 CPU 시간
- Shared Feature 계산 시간
- 무기별 Top-M 갱신 시간
- Target 변경 빈도
- First-hit Resolve 호출 수
- First-hit Resolve CPU 시간
- Blocking Geometry 비율
- Targetable Interceptor 비율
- Occlusion Cache hit / expire 빈도

Registry 갱신 비용, Spatial Index 유지 비용, GraphicsBuffer 비용 등은 `ARCH-100` Profiling 항목에서 측정한다.

## 16. Open Decisions

다음은 현재 Canon에서 확정하지 않는다.

| 영역 | 결정할 질문 | 다음 판단 조건 |
|---|---|---|
| Target Score | Logical Screen·거리·Mount Side·Retention·Target Type의 가중 방식을 어떻게 조합할지 | 플레이어 공격 의도와 분산 사격이 자연스럽고 동일 Score의 Stable 결과가 유지되는지 확인 |
| Top-M | 작은 고정값 후보 `2~4` 중 어떤 값을 사용할지 | Candidate 수·CPU 시간과 최대 4개 무기의 분산 품질을 함께 측정 |
| Target Retention | 최소 유지 Tick, 교체 Score 차이, 집중 Target의 Hysteresis 예외를 어떻게 정할지 | Target 변경 빈도와 무기·팔의 시각적 안정성을 확인 |
| Logical Targeting View | Combat Cone/FOV, Cruise Cone·Capsule, 화면비 처리 규칙을 어떻게 정할지 | 렌더 Camera 연출과 분리된 공격 의도가 모드별로 자연스럽게 읽히는지 확인 |
| Bounds | 대형 적과 Missile의 Targeting·Hit Bounds를 얼마나 보정할지 | 화면 가장자리 포함과 Missile 선택·피격이 편리하면서 불공정하지 않은지 확인 |
| Fire / Occlusion | `FireTolerance`, Cache 유지 Tick, Occlusion 우선도 감소 방식을 어떻게 정할지 | First-hit 자연스러움, Target 안정성, 고연사 CPU 비용을 함께 확인 |
| Instant Resolve 범위 | 어떤 직사 무기까지 적용하고 언제 World Projectile 또는 별도 설계로 분리할지 | 비행시간·지속 Collision·요격이 해당 무기의 핵심 Gameplay인지 판단 |
