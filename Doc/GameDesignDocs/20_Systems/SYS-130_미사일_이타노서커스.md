# SYS-130 미사일 시스템 요구사항 및 설계 — 이타노서커스형 군집

> **이타노서커스형 Missile 군집은 장식용 탄막이 아니라 실제 위협 판정을 가진 대량 적성 개체 집단이다. 동일 Salvo의 Missile은 공통 FSM과 개체별 파라미터 차이로 서로 다른 궤적·도달 시간·Overshoot·Reacquire를 만들고, 플레이어는 기동·자동 요격·국소 유폭으로 압박에 틈을 만들어 돌파한다.**

## 0. 문서 계약

### 0.1 이 문서가 결정하는 것
본 문서는 실제 위협 Missile과 이타노서커스형 군집의 고유 규칙을 정의한다. Lifecycle·FSM·Guidance, Salvo·Emitter 행동, 요격·폭발 요청, 궤적·near-miss·경보 표현, Missile 고유 비용과 검증 기준을 소유한다.

### 0.2 이 문서가 결정하지 않는 것
프로젝트 목표는 [PRJ-000](../00_Project/PRJ-000_프로젝트_통합기획_기준서.md)이 소유한다. PlayerState·SalvoContext·Scheduling·Spatial, Authority·Commit·Lifecycle·Pooling·Visual Runtime은 [ARCH-100](../10_Architecture/ARCH-100_전투_적성객체_아키텍처.md)을 따른다. 기동은 [SYS-110](SYS-110_플레이어_기동.md), 플레이어 무기의 Missile Targeting은 [SYS-120](SYS-120_자동타게팅_직사화기.md), 장비·빌드는 [SYS-140](SYS-140_세션_장비_빌드_익스트랙션.md), Emitter의 월드 역할은 [SYS-160](SYS-160_군도작전_전방지원.md), 세계관 사실은 [WORLD-100](../30_World/WORLD-100_세계관_Canon.md)이 결정한다.

이 문서는 공통 Runtime을 재정의하지 않고 Missile이 그 위에서 어떻게 행동하는지만 결정한다.

## 2. 목표

### 2.1 Gameplay 목표
- 플레이어에게 지속적인 회피·요격·포지셔닝 판단을 제공한다.
- Missile을 단순 탄환이 아니라 파괴 가능한 적성 객체로 인식시킨다.
- 모든 Missile 제거보다 **요격과 회피를 섞어 돌파하는 플레이**를 만든다.
- Emitter 제거와 이미 발사된 Missile 처리 사이에 전술 선택을 만든다.
- Overshoot와 Reacquire로 전방만 보는 플레이를 방지한다.
- 국소 유폭으로 플레이어가 직접 회피 공간을 만들 수 있게 한다.

### 2.2 연출 목표
- 동일 Salvo가 하나의 곡선으로 정렬되지 않게 한다.
- 상하·좌우 편향, 시간차 접근, 곡선 추적, Overshoot, Reacquire를 혼합한다.
- Trail·음향·경보가 실제 Missile 위치와 일치하게 한다.
- near-miss를 실제 위협의 결과로 보이게 한다.
- 수면 스키밍·탄착으로 군도 전장의 정체성을 강화한다.

### 2.3 성능 목표
- 개별 Missile의 Player Search·Target 평가를 제거한다.
- Player Target Sample을 Salvo 단위로 공유한다.
- Target Sample 갱신과 개별 Movement 빈도를 분리한다.
- 모든 Missile 간 검사와 전체 Missile 대상 폭발 검사를 금지한다.
- Pooling은 필수 전제가 아니라 측정 후 선택한다.
- Visual 밀도를 위해 Gameplay Missile 수를 무제한 증가시키지 않는다.

## 3. 핵심 개념

### 3.1 Missile
개별 `Missile`은 실제 Gameplay 위협이며 최소한 다음 상태를 가진다.

```text
Salvo reference
GuidanceState
IndividualSeed
Position / Velocity
Targetable / Damage state
Profile reference
```

공통 Target 정보는 개별 Missile마다 중복 보관하지 않는다.

### 3.2 Salvo
`Salvo`는 중앙 Simulation Controller가 아니라 공유 Context다.

- 동일 Emitter의 발사 묶음 식별
- Target Player와 Target Sample 공유
- Salvo Seed 공유
- Member 수와 발사 시퀀스의 기준 제공

공통 Runtime 형태는 `ARCH-100`의 `SalvoContext`를 따른다.

### 3.3 Emitter
Emitter는 Salvo의 Gameplay 원인이다. 함선 VLS, 방공 부표, 섬 방공 시설, Missile Drone 등이 될 수 있다. 월드 배치와 보상은 `SYS-160`이 소유한다.

### 3.4 Missile Profile과 개체별 편차
동일 계열 Missile의 불변 데이터는 Profile로 공유하고, Salvo 내부 차이는 Seed 기반 파라미터 분포로 만든다.

주요 파라미터:

| 파라미터 | 역할 |
|---|---|
| `LaunchDelay` | Salvo 내부 발사 시간차 |
| `LaunchAngleOffset` | 초기 발사각 차이 |
| `SeparationBias` | 상하·좌우 분산 방향 |
| `InitialSpeed` / `BoostSpeed` | 상태별 속도 |
| `HomingAggression` | 추적 강도 |
| `MaxSnapAngle` | 즉시 방향 전환 허용각 |
| `TurnRate` | 큰 방향 변화의 제한 선회 속도 |
| `AngularAcceleration` | 선택적 곡선 품질 보정 |
| `OvershootBias` | Target 통과 경향 |
| `ReacquireDelay` | 통과 후 재획득 지연 |
| `LateralCurveBias` / `VerticalCurveBias` | 궤적 편향 |
| `FuseInstability` | Burning·유폭 민감도 |

정확한 수치는 §16 Open Decisions에서 관리한다.

## 4. 요구사항

### 4.1 실제 위협과 정보 신뢰성
- 일반 Missile은 실제 충돌·피해 가능성을 가진다.
- 일반 Missile은 플레이어 공격의 Target이 될 수 있다.
- 판정 없는 장식 Missile·디코이는 기본 경로에서 사용하지 않는다.
- Trail, Burning, Detonation 표현은 실제 Gameplay 상태와 일치해야 한다.

### 4.2 공통 FSM 우선
궤적 차이만을 이유로 Missile 타입을 분리하지 않는다. 대형 Missile, 고고도 낙하형, 수면형처럼 Gameplay 규칙 자체가 달라질 때만 독립 Profile/Type을 검토한다.

### 4.3 요격 가능
- 모든 일반 Missile은 기본적으로 Targetable이다.
- 요격 시 HP 감소, 파괴, Burning/Unstable 전환 등 실제 결과가 발생한다.
- Targeting 우선순위 계산은 `SYS-120`이 소유한다.

### 4.4 국소 유폭
폭발은 주변 Missile 일부를 제거·불안정화·교란해 **짧은 돌파 공간을 만드는 수단**으로 사용한다. 일반 요격 한 번으로 전체 Salvo가 사라지는 구조는 피한다.

## 5. Missile Lifecycle

### 5.1 Gameplay Lifecycle
```text
Spawn / Arm
→ Launch Burst
→ Separation
→ Cruise Drift
→ Acquire
→ Homing Arc
→ Attack Commit
   ├─ Detonate
   └─ Overshoot → Reacquire → Homing Arc

손상 시
→ Burning / Unstable
→ Detonate 또는 제한적 계속 비행

종료 시
→ Despawn Request
→ ARCH-100 Lifecycle Commit
```

### 5.2 Pooling과 분리
Gameplay Lifecycle은 Pool 유무와 독립적이다.

```text
Gameplay Despawn
≠ 반드시 Object Destroy
≠ 반드시 Pool Return
```

Pooling 적용 여부는 `ARCH-100`의 측정 결과를 따른다.

### 5.3 Spawn 초기화
Spawn 시 최소한 다음이 확정되어야 한다.

- Salvo ID와 Member 순번
- Emitter ID
- Missile Profile
- Individual Seed
- 초기 Position / Forward / Velocity
- LaunchDelay와 개체별 편향 파라미터
- 초기 FSM 상태

Stable ID와 Spawn Commit은 `ARCH-100`을 따른다.

## 6. Missile FSM

### 6.1 상태
| 상태 | 역할 | 핵심 처리 |
|---|---|---|
| Spawn / Arm | 생성 초기화 | 발사 데이터 설정 |
| Launch Burst | Emitter 이탈 | 초기 가속, 큰 Snap 제한 |
| Separation | 군집 분산 | 상하·좌우 간격 확보 |
| Cruise Drift | 추적 전 접근 | 관성 이동 + 약한 곡률 |
| Acquire | Target Sample 반영 | DesiredDirection 계산 |
| Homing Arc | 주요 추적 | Snap 또는 제한 선회 |
| Attack Commit | 최종 돌입 | 급선회 축소, 충돌 위협 증가 |
| Overshoot | Target 주변 통과 | near-miss와 이탈 |
| Reacquire | 재추적 | 최신 Sample로 재진입 방향 생성 |
| Burning / Unstable | 손상 상태 | 불안정·유폭 민감도 증가 |
| Detonate | 폭발 요청 | ARCH Detonation Pipeline로 전달 |
| Despawn | 종료 | Despawn Request |

### 6.2 ECS 표현 원칙
FSM 상태 전이마다 Archetype을 바꾸지 않는다. 실제 데이터 구성이 바뀌는 경우가 아니라면 상태 값과 공통 Component를 유지한다.

### 6.3 상태별 계산 강도
| 상태 | Target Sample 의존 | Collision 관심도 | 비고 |
|---|---:|---:|---|
| Launch / Separation | 없음 | 낮음 | 발사·분산 |
| Cruise Drift | 낮음 | 낮음 | 접근 |
| Acquire | 높음 | 중간 | Guidance 설정 |
| Homing Arc | 중간 | 중간 | 추적 |
| Attack Commit | 낮음 | 높음 | 최종 위협 |
| Overshoot | 없음~낮음 | 중간 | near-miss |
| Reacquire | 중간 | 중간 | 재추적 |
| Burning | 낮음 | 높음 | 유폭 후보 |
| Detonate | 없음 | 폭발 Query 요청 | 1회성 Event 중심 |

정확한 Scheduling과 Simulation LOD는 `ARCH-100`을 따른다.

## 7. Guidance

### 7.1 Target Sample 사용
개별 Missile은 Player를 검색하지 않는다.

```text
Canonical PlayerState
→ ARCH Salvo Target Sample
→ Cached SalvoContext.TargetSample
→ SYS-130 Guidance
```

본 문서는 Sample로부터 개별 Missile의 `DesiredDirection`을 만드는 규칙만 소유한다.

### 7.2 기본 흐름
```text
TargetSample 읽기
→ FSM 상태 + 개체별 파라미터 적용
→ DesiredDirection 계산
→ CurrentDirection과 각도 비교

angle <= State.MaxSnapAngle
→ Snap Turn

angle > State.MaxSnapAngle
→ TurnRate 기반 제한 선회
```

### 7.3 Snap Turn
- `Acquire`와 `Homing Arc`에서는 작은~중간 방향 변화에 Snap Turn을 허용한다.
- 초기 비교값은 45° / 60° / 90° 등으로 둔다.
- `Attack Commit`에서는 Snap 허용각을 크게 줄이거나 진행 방향을 부분 고정한다.
- `Launch Burst` 직후 큰 Snap은 금지한다.
- `Reacquire`의 90° 초과 급선회는 검증 후 결정한다.

### 7.4 제한 선회
`MaxSnapAngle`을 초과하는 변화만 `TurnRate`로 처리한다. `AngularAcceleration`은 필수 규칙이 아니며 곡선 품질이 필요할 때만 추가한다.

### 7.5 Overshoot와 Reacquire
`OvershootBias`가 높은 Missile은 Target 근처를 지나쳐 측면·후방으로 이탈할 수 있다. 이후 `ReacquireDelay`가 끝나면 최신 Salvo Target Sample로 새로운 DesiredDirection을 만든다.

Overshoot는 단순 명중 실패가 아니라 군집 압박의 의도된 상태다.

### 7.6 예측 위치
일부 Profile은 다음과 같이 Target velocity를 사용할 수 있다.

```text
PredictedTarget = TargetSample.Position
                + TargetSample.Velocity × PredictionTime
```

모든 Missile에 예측을 강제하지 않는다.

### 7.7 Hot Path 금지사항
개별 Missile에서 다음을 수행하지 않는다.

- Player 목록 검색
- Player별 Target Score 계산
- Salvo 전체 Member 순회
- 모든 Missile 간 거리 검사
- 전역 Zone 검색

## 8. Salvo 행동

### 8.1 역할
Salvo는 공통 Target·Seed·발사 단위이고, 개별 Member 이동을 대신 계산하지 않는다.

### 8.2 내부 역할 분화
| 역할 | 주요 파라미터 |
|---|---|
| 선두 압박 | 짧은 LaunchDelay, 빠른 Commit |
| 측면 휘감기 | 큰 `LateralCurveBias` |
| 상하 교차 | 큰 `VerticalCurveBias` |
| near-miss | 높은 `OvershootBias` |
| 재획득 압박 | Reacquire 활성 |
| 유폭 후보 | 높은 `FuseInstability` |
| 후속 압박 | 긴 LaunchDelay 또는 느린 접근 |

### 8.3 군집 동기화 방지
동일 Salvo가 같은 Tick에 같은 행동을 하지 않도록 다음을 분산한다.

- LaunchDelay
- Seed / Member ordinal
- FSM 진입 시점
- CurveBias
- Overshoot / Reacquire 비율

Target Sample Scheduling은 `ARCH-100`을 사용한다.

### 8.4 Target 변경
Salvo의 Target Player 배정은 `ARCH-100`이 소유한다. Target이 바뀌면 SYS-130은 다음 유효 Sample부터 Guidance가 새 Target을 반영할 수 있어야 한다.

## 9. Missile Emitter

### 9.1 Emitter 인터페이스
Emitter는 최소한 다음 정보를 제공한다.

- Stable ID
- 발사 위치·방향
- Missile / Salvo Profile
- Member Count
- 발사 Event 또는 주기
- Target assignment와 연결할 정보

### 9.2 대표 형태
| Emitter | Missile 관점의 역할 |
|---|---|
| 방공 부표 | 반복 소규모 Salvo |
| Missile Drone | 이동식 소규모 압박 |
| 초계함 Pod | 중간 규모 Salvo |
| 함선 VLS | 대량 수직발사 Salvo |
| 모함 발사부 | 복합 위협 발생원 |
| 섬 방공 시설 | 고정 접근 억제 |

월드 배치와 보상은 `SYS-160`이 결정한다.

### 9.3 Emitter 파괴
- Emitter 파괴 시 신규 Salvo 생성을 중단한다.
- 이미 발사된 Missile은 독립 FSM을 유지한다.
- Emitter 파괴가 기존 Missile의 즉시 삭제를 의미하지 않는다.

## 10. 플레이어 요격

### 10.1 기본 원칙
- 모든 일반 Missile은 공격으로 파괴 가능하다.
- 요격과 회피가 모두 유효해야 한다.
- 요격 성공은 Trail 절단, 파괴, Burning 전환 등 명확한 피드백을 가져야 한다.

### 10.2 SYS-120 인터페이스
Missile은 `SYS-120`이 사용할 수 있도록 Targetable 상태와 필요한 Target Feature를 제공한다.

예:

- Targeting Bounds / Hit Bounds
- Position / Velocity
- Profile / Target Class
- 제한된 FSM 상태 정보

실제 Target Score와 복수 무기 Target Assignment는 `SYS-120`이 소유한다.

### 10.3 장비 상호작용 방향
| 장비 성격 | Missile 상호작용 |
|---|---|
| 고연사 직사 | 개별 Missile 빠른 요격 |
| 산탄·광역 | 근거리 복수 Missile 대응 |
| 관통형 | 정렬된 Missile 다중 대응 가능 |
| 폭발형 | 국소 유폭·불안정화 |
| 후방 대응 보조무장 | Overshoot / Reacquire 견제 |
| Flare / ECM 후보 | Acquire·Reacquire·Homing 약화 가능 |

장비 자체의 존재와 밸런스는 `SYS-140`에서 확정한다.

---

## 11. 폭발·유폭

### 11.1 시스템 역할
Missile 폭발은 다음 중 일부를 만든다.

- 인접 Missile 피해
- Burning / Unstable 전환
- Guidance 교란
- 짧은 추적 약화
- 국소 회피 공간 생성

### 11.2 실행 경계
SYS-130은 **Detonation Request를 만드는 조건**만 결정한다.

예:

- 충돌
- HP 0
- Fuse 조건
- Lifetime 종료
- Burning 중 추가 피격
- 특수 Profile의 근접신관

실제 처리는 `ARCH-100`을 따른다.

```text
Detonation Request
→ Spatial radius query
→ Damage / Detonation Event
→ Reduction / Authoritative Commit
```

### 11.3 군집 전멸 방지
- 거리에 따라 영향 감소
- 2차 연쇄 영향 축소 가능
- Launch / Separation 상태 유폭 저항 가능
- Separation으로 과밀 상태 완화
- 즉사보다 Burning·교란 전이를 우선할 수 있음
- 일반 Missile의 폭발 반경은 작게 유지

기존의 “일반 요격 1회로 2~5기 정리”는 확정값이 아니라 Prototype의 튜닝 목표 예시다.

## 12. 이타노서커스 연출

### 12.1 핵심 표현
| 요소 | 요구사항 |
|---|---|
| 시간차 | 대량 발사 인식은 유지하되 LaunchDelay로 미세한 차이 생성 |
| 혼재 궤적 | Snap 허용각, CurveBias, Overshoot, Reacquire 혼합 |
| 입체성 | 상하·좌우 편향 동시 사용 |
| near-miss | 실제 이동 경로상 Player 주변을 통과 |
| 재획득 | 일부 Overshoot Missile이 후방·측면에서 재진입 |
| 요격 리듬 | 요격 시 Trail 절단과 국소 폭발 표시 |
| 수면 연출 | 스키밍·탄착·수주로 군도 전장과 연결 |

### 12.2 궤적 원칙
- 직선 이동은 Launch·Attack Commit 등 필요한 구간에 한정한다.
- 같은 Salvo가 동일한 곡선·도달 시간으로 수렴하지 않게 한다.
- Attack Commit에서는 플레이어가 회피 방향을 읽을 수 있어야 한다.
- Homing Arc의 Trail은 접근 방향을 읽게 해야 한다.
- Missile이 화면 중앙의 Targeting 정보를 장시간 가리지 않게 한다.

### 12.3 Visual Runtime 경계
SYS-130은 다음 **표현 요구사항**만 소유한다.

- Missile body가 실제 Position / Forward를 반영
- Trail이 실제 경로와 일치
- Burning 표현이 실제 상태와 일치
- Detonation Event가 Explosion 표현의 근거가 됨
- near-miss가 실제 공간적 근접을 기반으로 발생

Visual State Buffer, GraphicsBuffer, VFX lifetime, Warm-up은 `ARCH-100`이 소유한다.

### 12.4 카메라·음향 경보
금지:

- 강제 카메라 회전
- 강제 Target lock 변경
- 조준점의 Gameplay 위치 변경
- 화면 중앙 장시간 가림
- 슬로모션 남발

표현 후보:

- 짧은 FOV Pulse
- 짧은 Camera Pullback
- Edge Shake
- 작은 Micro Roll
- Directional Audio Pan
- Near-miss Flash
- Low Bass Pulse

### 12.5 Logical Targeting 보호
카메라 연출은 `SYS-120`의 `LogicalTargetingView`를 바꾸지 않는다.

```text
Missile Warning → Render Camera Effect
SYS-120 LogicalTargetingView → unchanged
```

기존 문서의 구체적인 FOV·시간·Roll 수치는 Canon 값이 아니라 **테스트 시작값**으로만 사용한다.

## 13. 성능 요구사항

### 13.1 비용 구조와 절감 원리

| 비용 원인 | 제한 규칙 | 줄어드는 비용 | 감수하는 대가·검증점 |
|---|---|---|---|
| 개별 Missile의 Player 탐색·예측 | Target Assignment와 Sample을 Salvo 단위로 공유 | Player Search와 공통 Target 계산의 반복 제거 | Sample cadence를 낮춰도 직접 위협의 반응성이 유지되는지 확인 |
| 모든 상태의 동일 빈도 처리 | FSM 상태와 거리에 따라 Sample·Collision 관심도를 나눔 | 원거리·비공격 상태의 불필요한 고비용 판정 감소 | Attack Commit과 근거리 상호작용의 정확도는 유지 |
| Spawn·Acquire·Commit·Detonation 집중 | Stable Phase와 공통 Budget으로 실행 시점을 분산 | 한 Tick에 몰리는 CPU·Structural Change spike 억제 | 즉시 반영해야 하는 Gameplay 결과를 지연하지 않음 |
| 폭발 시 전체 Missile 검사 | Spatial radius query로 영향 후보만 처리 | 전수·상호 비교 비용 제거 | Spatial 유지 비용과 전략 선택은 `ARCH-100` 책임 |
| 반복 Spawn·Despawn | Create/Destroy와 Reuse를 A/B 측정한 뒤 Pooling 선택 | 유효한 대상에서 churn과 Structural Change 감소 가능 | inactive memory·reset·구현 복잡도가 늘 수 있음 |
| 화면 밀도를 실제 개체 수만으로 확보 | Trail·시간차·곡선·near-miss·수면 연출·음향을 함께 사용 | 표현 밀도를 위해 Gameplay Missile 수만 늘리는 것을 방지 | Visual build·VFX 비용은 별도로 측정 |

개별 Missile Hot Path는 Salvo Target Sample 읽기, Guidance·Movement, 필요한 Contact·near-threat 처리로 제한한다. 모든 Missile 간 검사와 Zone Search는 사용하지 않는다. Simulation LOD, Spatial 전략, 최종 Rendering 기술은 `ARCH-100`이 결정한다.

### 13.2 Profiling
공통 지표에 더해 다음을 확인한다.

- Active Missile / Salvo 수
- Salvo Target Sample 수
- Guidance / Movement CPU time
- Attack Commit Missile 수
- Detonation Request / Query 수
- Burning / Reacquire 활성 수
- Spawn / Despawn 수
- Create/Destroy 대비 Reuse 비용
- Missile Visual State build 비용

## 15. Prototype과 검증

아래 Prototype은 구현 범위 계획이며 완료 상태를 뜻하지 않는다. 검증 표도 판정할 질문이지 확인된 결과가 아니다.

### 15.1 1차 Prototype
| 항목 | 포함 | 후순위 |
|---|---|---|
| Emitter | 단일 Emitter | 복수 Emitter 연계 |
| Salvo | 여러 Salvo, Member 편차 | 복잡한 멀티 Target |
| FSM | Launch, Separation/Drift, Acquire, Homing, Commit, Detonate | Reacquire/Burning 고도화 |
| Target | Shared Salvo Target Sample | 개별 Missile Search는 사용하지 않음 |
| Guidance | Snap + TurnRate | AngularAcceleration |
| 요격 | 직사 화기로 파괴 가능 | 모든 장비 차등 |
| 폭발 | 소형 폭발 + 인접 Missile 일부 영향 | 복잡한 Chain |
| 경보 | 기본 FOV / near-miss 반응 | 전체 음향·Roll 세트 |
| Lifecycle | Create/Destroy vs Reuse 비교 | Pooling 적용 여부 판단 |

### 15.2 2차 Prototype
- Salvo 내부 역할 분화
- Overshoot / Reacquire
- Burning / Unstable
- 국소 유폭과 Guidance 교란
- 후방·측면 요격 상호작용
- 수면 스키밍·탄착
- Camera Pullback / Micro Roll / Directional Audio
- 필요 시 Simulation LOD / Salvo Proxy A/B 검증

### 15.3 검증 질문
| 영역 | 질문 |
|---|---|
| Gameplay | Missile이 단순 탄막이 아니라 파괴 가능한 적으로 느껴지는가 |
| Gameplay | 요격과 회피를 섞어 돌파하는 플레이가 발생하는가 |
| Guidance | Snap Turn이 불공정 순간회전보다 의도된 고기동으로 보이는가 |
| Guidance | Attack Commit의 회피·요격 타이밍을 읽을 수 있는가 |
| 군집 | 실제 위협 Missile만으로 충분한 화면 밀도가 생기는가 |
| 유폭 | 한 번의 요격이 전체 Salvo를 지우지 않는가 |
| 연출 | Trail·near-miss가 실제 Missile 위치와 일치하는가 |
| 경보 | 카메라 경보가 입력·조준·LogicalTargetingView를 방해하지 않는가 |
| 성능 | Shared Target Sample이 개별 Player read/prediction을 줄이는가 |
| 성능 | 대량 Salvo에서 frame time spike의 주 원인이 무엇인가 |
| 성능 | Pooling 또는 Reuse가 Create/Destroy보다 실제 이득이 있는가 |

## 16. Open Decisions

| 영역 | 결정할 질문 | 다음 판단 조건 |
|---|---|---|
| Guidance | Homing `MaxSnapAngle` 후보 45°·60°·90°, Attack Commit 허용각, Reacquire 90° 초과 선회, 상태별 `TurnRate`, `AngularAcceleration` 사용 여부를 어떻게 정할지 | Snap이 불공정한 순간회전으로 보이지 않고 Commit의 회피·요격 타이밍이 읽히는지 비교 |
| Salvo 규모·갱신 | Target Sample cadence와 Member Count를 어떻게 정할지 | 대량 Salvo의 CPU 시간·frame spike와 직접 위협의 반응성을 함께 측정 |
| 군집 구성 | Overshoot와 Reacquire 비율을 어떻게 정할지 | 실제 위협 Missile만으로 궤적 다양성과 측후방 압박이 읽히는지 확인 |
| 폭발·손상 | 국소 유폭 범위·효과와 Burning 지속시간을 어떻게 정할지 | 한 번의 요격이 전체 Salvo를 지우지 않으면서 짧은 돌파 공간을 만드는지 확인 |
| Missile 타입 | 언제 공통 FSM의 Profile 차이가 아니라 독립 타입으로 분리할지 | 궤적 차이가 아니라 Gameplay 규칙과 데이터 구성이 실제로 달라질 때 판단 |
| 경보 | FOV·Camera·음향 경보의 강도를 어떻게 정할지 | 입력·조준·LogicalTargetingView를 방해하지 않으면서 접근 방향이 읽히는지 확인 |
| Flare / ECM | 장비 상호작용을 채택할지, Acquire·Reacquire·Homing에 어떻게 영향을 줄지 | `SYS-140`에서 해당 장비와 비용 구조를 구체화할 때 공동 결정 |

Individual/Salvo Spatial, Spatial 갱신, Pooling, Simulation LOD, Network 압축, Rendering 경로는 [ARCH-100](../10_Architecture/ARCH-100_전투_적성객체_아키텍처.md)의 Open Decision에서 관리한다.
