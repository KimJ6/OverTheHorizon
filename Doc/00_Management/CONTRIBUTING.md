# 저장소 작업 가이드

이 문서는 1인 개발에서 변경 이유를 찾을 수 있고 필요할 때 되돌릴 수 있는 Git 이력을 남기기 위한 최소 규칙이다. 작은 작업마다 Issue·브랜치·Pull Request를 만들지 않는다. 변경 위험과 검토 필요성이 커질 때만 절차를 늘린다.

문서의 작성·Owner·Revision·Archive 기준은 [DOCS-000](DOCS-000_문서관리_운영가이드.md)을 따른다.

## 1. 기본 원칙

- `main`은 가능한 한 실행 가능하고 이해할 수 있는 상태로 유지한다.
- 커밋 하나에는 설명 가능한 하나의 변경 목적을 담는다.
- 커밋 전에는 변경 파일과 Diff를 확인하고, 위험에 맞는 검증을 수행한다.
- 관련 없는 수정과 자동 포맷 변경을 한 커밋에 섞지 않는다.
- 브랜치·Issue·PR·CI는 도움이 될 때 사용하며 작업 자체보다 관리 절차가 커지지 않게 한다.

## 2. 작업 방식 선택

| 상황 | 기본 방식 |
|---|---|
| 오탈자, 문구 정리, 작은 설정 변경 | `main`에서 수정·검증 후 직접 커밋 가능 |
| 범위가 작고 쉽게 되돌릴 수 있는 코드 변경 | 직접 커밋 또는 짧은 브랜치 |
| 여러 시스템에 영향을 주는 기능·리팩터링 | 작업 브랜치 권장 |
| 실험, 장기 작업, 현재 상태를 깨뜨릴 수 있는 변경 | 작업 브랜치 사용 |
| 외부 검토, 원격 CI, 공개 변경 설명이 필요한 작업 | PR 사용 |

저장소에 Branch Protection이나 필수 CI가 설정되면 해당 제약을 우선한다. 공동 작업자가 생기면 공유 브랜치의 변경을 임의로 덮어쓰지 않고 필요한 범위에서 PR과 리뷰를 사용한다.

## 3. 브랜치

브랜치를 사용할 때는 하나의 작업 목적만 담고 오래 방치하지 않는다.

이름은 다음 형식을 권장한다.

```text
<type>/<description>
<type>/<issue-number>-<description>
```

주요 Type:

| Type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작을 유지하는 구조 변경 |
| `perf` | 성능 개선 |
| `docs` | 문서 변경 |
| `test` | 테스트 변경 |
| `build` | 빌드·의존성 변경 |
| `ci` | CI 설정 변경 |
| `chore` | 기타 유지보수 |

예: `feat/player-movement`, `fix/73-camera-jitter`, `docs/canon-cleanup`

`work`, `final`, `fix2`처럼 목적을 알 수 없는 이름은 사용하지 않는다.

## 4. 커밋

커밋 메시지는 다음 형식을 권장한다.

```text
<type>(<scope>): <subject>
<type>: <subject>
```

예:

```text
feat(player): add boost movement
fix(camera): prevent rotation jitter
perf(targeting): reduce candidate queries
docs: clarify movement validation status
```

`scope`는 구분에 도움이 될 때만 사용한다. 종류를 미리 세분화하거나 빈 scope를 억지로 채우지 않는다.

커밋 전에는 다음을 확인한다.

1. 변경 목적을 한 문장으로 설명할 수 있는가?
2. 의도하지 않은 파일이나 임시 자료가 포함되지 않았는가?
3. 관련 검증을 수행했으며 결과를 과장하지 않았는가?
4. 현재 상태에서 작업을 이어가거나 되돌릴 수 있는가?

완성되지 않은 중간 저장 커밋은 로컬 작업 이력으로 사용할 수 있다. 공유하거나 `main`에 남길 때는 의미가 드러나는 단위와 메시지로 정리한다.

## 5. 검증과 자체 검토

변경 위험에 맞게 필요한 항목만 확인한다.

- 코드: 빌드, 관련 테스트, 직접 실행, 성능 측정 중 해당하는 것
- 문서: Owner, 현재 상태, 링크, Metadata, Revision, 중복·낡은 내용
- 데이터·에셋: 참조 누락, Import 결과, 실제 Scene 또는 빌드 동작
- 공통: `git status`와 `git diff`로 의도한 변경만 포함됐는지 확인

테스트가 없거나 실행하지 못했다면 통과한 것처럼 쓰지 않는다. 성능 개선은 조건을 맞춘 측정이 있을 때만 결과로 표현한다.

## 6. Pull Request와 리뷰

PR은 모든 변경의 의무 절차가 아니다. 다음 중 하나에 해당하면 사용을 권장한다.

- 변경 범위가 커서 독립된 검토 화면이 유용하다.
- 여러 시스템·문서의 책임 경계가 바뀐다.
- 원격 CI 결과를 확인해야 한다.
- 외부 기여자와 의견·승인 기록을 남겨야 한다.
- 장기 브랜치를 `main`에 합치기 전에 변경 목적과 검증을 정리해야 한다.

PR 본문에는 필요한 만큼만 적는다.

```markdown
## 변경 내용

## 변경 이유

## 검증
```

복잡한 변경에서만 설계 결정, 성능 영향, Breaking Change, 관련 Issue를 추가한다. 병합 방식은 커밋을 하나로 정리할 가치가 있으면 Squash and Merge를 사용하고, 개별 커밋의 의미가 있으면 그대로 보존한다.

## 7. 안전과 이력

- `main`과 공유 브랜치에는 강제 Push를 사용하지 않는다.
- 개인 작업 브랜치에서 꼭 필요하면 `--force`보다 `--force-with-lease`를 사용한다.
- 충돌은 변경 의도를 확인한 뒤 해결하고 관련 동작을 다시 검증한다.
- 큰 삭제·이관·의존성 변경 전에는 정확한 대상과 복구 방법을 확인한다.
- Issue는 장기 추적, 버그 재현, 외부 협의가 필요할 때만 만든다.

Git 이력에는 무엇을 바꿨고 왜 바꿨는지 찾을 수 있을 정도의 정보만 남긴다. 상세한 현재 설계는 해당 Canon이 소유하며 커밋 메시지나 PR 본문에 중복해서 유지하지 않는다.

## 8. 최소 작업 흐름

작은 작업:

```text
수정
→ Diff 확인
→ 필요한 검증
→ Commit
→ 필요할 때 Push
```

위험하거나 큰 작업:

```text
작업 브랜치 생성
→ 수정과 중간 검증
→ Diff·영향 범위 확인
→ Commit
→ 필요하면 PR·CI·리뷰
→ main에 병합
→ 작업 브랜치 정리
```
