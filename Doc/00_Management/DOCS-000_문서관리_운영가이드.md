# DOCS-000 게임 설계 문서 작성·관리 가이드

이 가이드는 1인 개발에서 현재 설계를 구현하고 다음 판단을 내리는 데 필요한 기록만 남기기 위한 기준이다. 문서의 주 독자는 구현하고 판단할 미래의 개발자 자신이며, 포트폴리오 설명은 현재 선택과 근거를 나중에 재구성할 수 있을 정도로 남긴다. 문서 작성 자체를 개발 단계로 만들지 않고, 설계나 판단이 바뀔 때 기존 내용을 현재 상태로 고친다.

## 0. 목적과 적용 원칙

### 0.1 적용 대상과 문서의 역할

이 문서는 `Doc` 아래 게임 설계 문서와 문서 운영 가이드에 적용한다. 실제 게임 규칙·기술 선택·세계관 사실은 각 Owner 문서가 결정한다. 문서 기준을 맞추기 위해 미정인 규칙·수치·비교 이력·검증 결과를 추론해 채우지 않는다.

| 문서 | 책임 |
|---|---|
| DOCS-000 | 유형별 책임, 작성·근거·갱신·수명주기 기준 |
| [CONTRIBUTING](CONTRIBUTING.md) | 브랜치·커밋·PR·리뷰·병합 등 저장소 작업 절차 |
| [PRJ-000](../GameDesignDocs/00_Project/PRJ-000_프로젝트_통합기획_기준서.md) | 프로젝트 목표와 현재 Canon 목록·문서 지도 |
| 각 Owner Canon | 해당 영역의 현재 규칙과 선택 이유 |

Canon 문서는 현재 구현과 판단을 위한 기준이다. 작업 일지나 완성된 포트폴리오 원고가 아니다. 포트폴리오에서는 Canon과 근거 자료를 바탕으로 문제·선택·결과를 별도로 편집한다.

### 0.2 필요한 만큼만 적용한다

‘필수’와 ‘해야 한다’는 적용 대상에서 지킬 규칙이다. ‘권장’은 다른 방법을 선택할 수 있는 기본안이다. 조건이 붙은 규칙은 그 조건이 발생할 때만 적용한다. 예시는 설명용이며 게임의 확정값이 아니다.

규칙에 필요한 정보는 기존 문단에 통합한다. 항목마다 새 제목·표·빈 양식을 만들거나 관련 없는 항목을 `해당 없음`으로 채우지 않는다. 작은 선택은 한두 문장으로 충분할 수 있으며, 플레이 경험·비용·성능을 크게 바꾸는 선택일수록 이유와 근거를 더 자세히 남긴다.

## 1. 책임과 문서 효력

### 1.1 One Rule, One Owner

Markdown 파일을 문서 원본으로 사용한다. Obsidian은 탐색·편집 도구이고 Git은 변경 이력·복구 수단이다.

하나의 규칙에는 하나의 Owner를 둔다. 선택의 상세 규칙과 현재 이유도 그 Owner에서 관리한다. 다른 문서는 독자의 이해에 필요한 짧은 요약과 링크만 제공한다. 현재 Owner 목록은 PRJ-000의 문서 지도를 따른다.

작성일이나 Revision이 더 높아도 다른 문서의 책임을 덮어쓰지 않는다. 충돌하면 Owner의 규칙을 먼저 정리하고 영향받는 문서의 요약과 링크를 갱신한다. Owner가 불분명하면 Open Decision으로 남기며 임의로 합치지 않는다.

### 1.2 Canon·초안·과거 기록

| 구분 | 의미 |
|---|---|
| Canon | 현재 채택된 설계 기준 |
| Draft | 검토 중인 제안이며 현재 기준을 대체하지 않음 |
| Open Decision / Open Canon | 아직 확정되지 않은 결정 |
| Archive | 범위를 정해 보존한 과거 설계·실험·설정 연구 |
| Git History | 같은 문서의 과거 버전과 일반 수정 이력 |

Canon 채택은 구현 완료나 효과 검증을 뜻하지 않는다. 현재 선택의 이유는 Canon에 남기고, 시간순 작업 경위는 Git이나 필요한 Archive에서 관리한다.

## 2. 가벼운 작성 원칙

### 2.1 핵심부터 짧게 쓴다

문서 첫머리에서 이 문서가 답하는 질문과 현재 핵심 선택을 알 수 있게 쓴다. 구현·확인 상태나 중요한 한계를 모르면 계획을 성과로 오인할 수 있을 때만 함께 밝힌다. 긴 배경·책임 목록·구현 세부사항은 뒤에 둔다.

평문과 `~한다` 문체를 기본으로 한다. 한 문장·단락에는 하나의 중심 판단을 두고, 같은 개념에는 같은 용어를 쓴다. 규칙·권장안·후보·확인된 결과는 표현으로 구분한다.

캐주얼하게 쓴다는 것은 구어체로 쓰거나 근거를 생략한다는 뜻이 아니다. 명사형 보고 문구, 장식적인 도입, 같은 결론의 반복을 줄이고 필요한 조건과 한계를 직접 쓰는 것을 뜻한다.

### 2.2 주요 결정의 최소 설명

주요 결정은 핵심 경험, 플레이 판단, 공통 구조, 정확성·반응성, 제작 범위·비용, 책임 경계를 유의미하게 바꾸는 선택이다. 주요 결정은 다음 내용을 연결해 설명한다.

1. 무엇을 선택했는가
2. 어떤 문제·목표 때문에 선택했는가
3. 그 선택이 무엇을 바꾸며 왜 작동한다고 보는가
4. 무엇을 감수하고 현재 어디까지 확인했는가

비교안·수치·출처·상세 검증 절차는 실제 판단이나 주장을 이해하는 데 필요할 때만 추가한다. 검토하지 않은 대안을 검토한 것처럼 쓰지 않는다. 개별 필드·예외·튜닝값은 상위 결정의 이유를 바꾸지 않는 한 다시 논증하지 않는다.

목적·목표·수단·결과를 구분한다. 확인한 사실, 그 의미에 대한 해석, 해석을 바탕으로 한 선택, 확인하지 못한 한계를 한 문장에 섞어 기대 효과를 결과처럼 쓰지 않는다.

### 2.3 리소스와 비용을 구체적으로 쓴다

`리소스`나 `비용`만 쓰지 않고 해당하는 대상을 특정한다.

- 런타임 자원: CPU·GPU 시간, 메모리·할당, 로딩·Physics·렌더링·통신 작업
- 제작 자원: 에셋·콘텐츠·데이터 제작량과 변형 수
- 개발·유지보수 자원: 구현·변경·디버깅·연결·인수인계 비용
- 검증 자원: 튜닝 조합, 테스트·측정·QA·검토 비용

절감을 주장할 때는 기존 비용, 줄어드는 원리, 대신 늘어나는 비용을 밝힌다. 규모나 성능 개선을 결과로 말하려면 §4에 맞는 근거가 있어야 한다. 모든 문서가 모든 리소스를 다루지는 않으며, §3의 책임과 실제 결정에 관련된 것만 쓴다.

### 2.4 형식은 설명 역할에 맞춘다

이유와 인과는 문단, 병렬 비교는 표, 작업 순서는 번호 목록, 복잡한 구조·상태 전이는 도식을 권장한다. 표와 도식이 문장보다 이해를 돕지 않으면 만들지 않는다. 마지막에 첫머리와 같은 요약을 반복하지 않는다.

H1은 문서 제목 하나에 사용하고 H2·H3 순서로 계층을 유지한다. 프로젝트 고유 개념과 약어는 첫 등장에 설명하고 코드 식별자는 정확히 보존한다. 이미지에는 대체 설명을 제공하며 색상만으로 의미를 전달하지 않는다.

## 3. 문서 유형별 책임

이 절은 유형마다 달라지는 판단 대상만 정의한다. 아래 인과 관계는 주요 선택을 설명할 때 확인할 질문이지 고정 제목이나 작성 양식이 아니다. 다른 Owner가 소유한 상세 규칙은 복제하지 않는다.

| 유형 | 주로 답할 질문 | 소유하는 판단 | 주요 인과와 리소스 |
|---|---|---|---|
| PRJ | 어떤 게임을 왜 만드는가? | 프로젝트 정체성, 목표 경험, 필러, Core Loop, 범위·MVP, Canon 지도 | 바꾼 게임 전제 → 시스템 결합 → 반복 판단 → 목표 경험. 플랫폼·콘텐츠 범위·재사용·우선순위 |
| ARCH | 어떤 제약에서 이 구조가 적합한가? | 공통 Runtime, 데이터 흐름, Authority, 공통 책임, 성능 Budget | 부하·제약 → 고비용 작업 → 구조 선택 → 줄고 늘어나는 비용. 런타임·중복 구현·통합 비용 |
| SYS | 규칙이 어떤 플레이 판단을 만드는가? | 개별 Gameplay System의 경험 목표, 규칙, 상태·입출력, 인터페이스·요구 | 정보 → 규칙 → 선택 → 결과·피드백 → 반복 행동. 객체·쿼리·할당, 제작 변형, 튜닝·테스트 조합 |
| WORLD | 무엇이 세계의 사실이며 어떤 기능을 하는가? | 설정 사실, 인과·범위·예외, 공개 정보, 미확정 설정과 현재 창작 의도 | 설정 → 공개 방식 → 해석·기대 → 감정·선택. 공통 설정·에셋·용어의 재사용과 정합성 비용 |
| Archive | 당시 무엇을 시도했고 무엇이 남았는가? | 범위가 정해진 과거 시도·관찰·교훈과 적용 한계 | 문제·가설 → 시도 → 관찰 → 당시 변경 → 현재 교훈. 실제 관찰된 비용만 보존 |
| Management | 언제 무엇을 적용하는가? | 운영 기준, 책임, 절차·예외·완료 조건 | 운영 문제 → 규칙 → 행동 → 줄어드는 오류·중복. 탐색·갱신·검토 비용 |

### 3.1 유형별 경계

- PRJ는 여러 시스템을 묶은 프로젝트 판단을 설명하고 시스템별 실험 로그나 세부 알고리즘을 복제하지 않는다.
- ARCH는 구조가 지원하는 요구를 PRJ·SYS에서 받아오며 구조 자체가 재미를 증명한다고 쓰지 않는다.
- SYS는 기능이 규칙대로 동작하는 것과 목표 판단·행동이 나타나는 것을 구분한다. 기능 PASS를 재미 가설의 성공으로 쓰지 않는다.
- WORLD는 세계 내부의 사실과 현재 창작 의도를 구분한다. 모든 설정에 경쟁 작품 비교·성능·제작비 분석을 붙이지 않는다.
- Archive는 상단에 현재 Canon이 아님을 밝히고 관련 Owner를 연결한다. 당시 관찰과 현재 재평가를 구분한다.
- Management는 다른 운영 문서나 게임 설계의 결정을 대신하지 않는다.

## 4. 현재 상태와 근거

### 4.1 필요한 상태만 밝힌다

설계 채택, 구현, 검증은 서로 다른 상태다. 하나의 상태값으로 합치지 않는다. 계획을 구현 결과로 오인할 가능성이 있을 때 문장이나 작은 표로 필요한 상태만 밝힌다. 모든 세부 항목에 상태표나 YAML 필드를 추가하지 않는다.

- 설계: 채택·후보·폐기 등 현재 판단
- 구현: 미구현·부분 구현·구현
- 근거: 직접 확인·비교 측정·외부 관찰 등 실제로 확보한 자료
- 기록 부재: 미실시가 확인되면 `미검증`, 수행 여부를 모르면 `근거 미기록/확인 필요`

정보가 없으면 확인 필요로 남긴다. 같은 정보에서 여러 해석이나 선택이 가능하면 Open Decision으로 다룬다. 정보 부족을 임의의 수치로 채우거나 해석 차이를 단정적인 문장으로 숨기지 않는다.

### 4.2 주장에 필요한 만큼 확인한다

근거 형식보다 주장 범위를 맞추는 것이 우선이다.

| 근거 | 말할 수 있는 범위 |
|---|---|
| 직접 구현·조작 확인 | 현재 빌드의 동작과 개발자의 현재 채택 판단 |
| 조건을 맞춘 비교 측정 | 해당 조건에서의 성능·비용 차이 |
| 플레이 관찰 | 관찰한 상황과 참여자에게 나타난 이해·행동 |
| 외부 자료 | 출처가 다루는 버전·조건·범위 |

혼자 직접 플레이해 만족했다는 판단은 다음 단계로 넘어갈 근거가 될 수 있다. 이를 모든 사용자에게 재미있음이 입증되었다거나 객관적 성능이 개선되었다는 주장으로 확대하지 않는다.

단순한 구현 확인은 짧은 결론으로 충분하다. 수치 개선, 외부 공개 성과, 일반화된 사용자 경험을 주장할 때는 비교 조건·버전·단위·측정 또는 관찰 범위와 한계를 남긴다. 원시 로그·영상·Profiler 캡처는 필요한 경우 증거 자료로 보존하고 Owner에는 현행 결론만 연결한다.

`PASS` 조건은 판정 기준이지 통과 기록이 아니다. 목표값·추정값·실측값을 구분한다. 출처는 해당 주장 가까이에 두고, 확인하지 않은 원자료를 읽거나 검증한 것처럼 인용하지 않는다.

### 4.3 Open Decision

미정 항목은 최소한 `결정할 질문`과 `결정에 필요한 조건 또는 다음 행동`을 적는다. 실제 후보나 대가가 판단에 필요하면 함께 남긴다. 담당자·일정은 정해진 경우에만 추가한다.

결정되면 현재 규칙과 선택 이유를 본문에 통합하고 미정 목록에서 제거한다. 채택 사실을 검증 성공으로 바꾸어 쓰지 않는다.

## 5. 갱신과 내용 정리

### 5.1 갱신 시점

다음 중 하나가 실제로 바뀌었을 때 관련 문서를 갱신한다.

- 현재 규칙·선택·Owner 또는 문서 간 경계
- 구현 상태가 문서의 해석을 바꿀 정도의 차이
- 기존 결론을 지지하거나 뒤집는 근거·한계
- 다음 판단에 필요한 Open Decision

단계를 끝냈다는 이유만으로 모든 관련 문서를 다시 작성하지 않는다. 결론과 상태가 그대로면 갱신하지 않아도 된다.

### 5.2 남길 내용과 지울 내용

내용을 추가하거나 유지하려면 다음에 답할 수 있어야 한다.

1. 이 문서의 Owner 범위에 속하는가?
2. 현재 판단·구현·재검토에 필요한가?
3. 다른 곳과 중복되지 않는가?
4. 현재도 유효하거나 적용 범위가 명확한가?

현재 결론과 무관한 작업 과정, 대화 경위, 완료된 TODO, 해결된 Open Decision, 중복 설명, 효력을 잃은 표·예시는 제거하거나 적합한 위치로 옮긴다. 반대로 현재 선택을 이해하는 데 필요한 고유 근거, 비교 대상, 중요한 제약·반례·측정 조건은 단순 정리 대상으로 삭제하지 않는다.

### 5.3 추가보다 교체한다

규칙이나 판단이 바뀌면 기존 설명을 현재 상태로 고쳐 쓴다. 예전 문장을 남긴 뒤 `수정`, `추가`, `이후 변경` 문단으로 덮어쓰지 않는다. 실행별 결과도 같은 질문의 현행 결론으로 갱신한다.

문서 자체의 변경 이력·작업 보고는 본문에 누적하지 않고 Git·Diff·PR에서 확인한다. 독자가 당장 취할 행동이 있는 임시 전환 안내만 문서당 한 개의 짧은 블록으로 허용하며, 적용 대상·행동·제거 조건을 적고 조건이 끝나면 없앤다.

문서 전체의 글자 수 상한은 두지 않는다. 분량을 맞추려고 필요한 명세를 지우거나 파일을 기계적으로 쪼개지 않는다. 새 절·표·도식은 기존 내용과 다른 질문이나 설명 역할이 있을 때만 추가한다.

## 6. 파일·Metadata·링크

### 6.1 폴더와 파일명

Obsidian Vault는 `Doc`을 사용한다.

| 경로 | 역할 |
|---|---|
| `Doc/00_Management` | 문서·저장소 운영 기준 |
| `Doc/GameDesignDocs/00_Project` | PRJ |
| `Doc/GameDesignDocs/10_Architecture` | ARCH |
| `Doc/GameDesignDocs/20_Systems` | SYS |
| `Doc/GameDesignDocs/30_World` | WORLD |
| `Doc/GameDesignDocs/90_Archive` | 과거 설계·실험·설정 연구 |

Canon 파일명은 `<ID>_<짧고_명확한_한글명>.md`로 작성하고 `최종`, 날짜, 버전 접미사를 붙이지 않는다. `document_id`는 제목이 바뀌어도 유지한다. 책임 자체가 분리되거나 재정의될 때만 새 ID를 검토한다.

Owner가 불분명한 메모는 필요할 때 `Doc/90_Inbox`에 임시 보관할 수 있다. Inbox의 내용은 Canon이 아니며 Owner가 결정되면 이관하거나 제거한다.

### 6.2 Metadata

모든 관리 대상 문서는 `document_id`, `title`, `document_type`, `status`, `last_updated`를 둔다. Canon과 Management는 의미 있는 단계가 필요할 때 `revision`과 `scope`를 둔다.

다음 필드는 실제 관계가 있을 때만 사용한다.

| 필드 | 용도 |
|---|---|
| depends_on | 규칙을 받아오는 Owner ID |
| interfaces | 직접 상호작용하는 문서 ID |
| supersedes | 대체하는 문서 식별 정보 |
| source_documents | 문서 작성 출처 이력. 개별 주장의 근거를 대신하지 않음 |
| canonical_replacement | Archive를 대체한 Canon ID |
| canonical_documents | PRJ가 관리하는 현재 Canon ID 목록 |

`document_type`은 project, architecture, system, world, archive, management를 사용한다. 게임 설계의 `status`는 canonical, draft, superseded, archive이며 Management는 active, draft, retired를 사용할 수 있다. `last_updated`는 `YYYY-MM-DD`로 기록한다.

### 6.3 Revision과 링크

Git은 실제 변경 이력을, `revision`은 사람이 판단할 의미 있는 규칙 단계를 나타낸다. 오탈자·형식·같은 의미의 표현 정리는 Revision을 유지한다. 같은 책임 안의 규칙·결론이 바뀌면 Minor, 핵심 책임·구조가 크게 바뀌면 Major를 올린다. `last_updated`는 의미 있는 내용 변경 시 갱신한다.

표준 Markdown 링크와 저장소 내부 상대경로를 사용한다. Metadata 관계는 ID로 표현하고 클릭 가능한 링크는 본문에 둔다. 제목·파일·책임을 바꾸면 파일 링크와 절 앵커를 확인한다. 모든 ID 반복에 링크를 붙이거나 그래프 모양을 위해 링크를 늘리지 않는다.

## 7. 생성·보관·폐기

### 7.1 새 문서를 만드는 조건

| 대상 | 생성·보존 조건 |
|---|---|
| 새 Canon | 기존 Owner에 넣으면 책임이 혼재하고, 독립적으로 설계·검토할 수 있으며, 다른 문서에서 독립 단위로 참조할 가치가 있을 때만 생성한다 |
| Archive | 과거 시도·폐기안의 이유와 결과에 재사용 가치가 있고 Git Diff만으로 맥락을 이해하기 어려울 때 만든다 |
| 증거 파일 | 주장을 재확인하는 데 필요한 원시 로그·영상·Profiler 캡처 등을 관련 Owner와 대상 버전에 연결해 보존한다 |
| 일반 문구 수정 | Git 이력으로 관리하며 수정마다 Archive·보고서·계획서를 만들지 않는다 |

단순히 문서가 길거나 Gameplay·Presentation·Performance가 다르다는 이유만으로 Canon을 분리하지 않는다. 같은 Canon의 과거 버전을 Archive에 복사하지 않는다.

### 7.2 이관과 폐기

Canon을 대체할 때는 대체 Owner를 결정하고 필요한 현재 규칙·근거를 이관한 뒤 참조를 갱신한다. 대체 문서에는 `supersedes`를 기록하고 기존 문서는 재사용 가치에 따라 Archive·superseded 또는 삭제로 처리한다.

현재 책임과 무관한 설명은 제거할 수 있다. 분석 가치가 있는 과거 판단, 중요한 반례, 재현에 필요한 유일한 증거를 함께 삭제하지 않는다. 이관·삭제 후에는 해당 자료를 인용한 주장과 링크를 확인한다.

## 8. 변경 절차와 점검

### 8.1 변경 절차

1. 바꿀 규칙과 근거의 Owner, 현재 구현·확인 상태를 확인한다.
2. 기존 설명을 대체·통합하고 현재 규칙·이유·미정 사항만 남긴다.
3. 의존 관계와 본문 링크로 영향받는 문서를 확인한다.
4. Metadata·Revision·날짜·링크와 아래 점검 항목을 확인한다.
5. 저장소 반영은 CONTRIBUTING을 따른다.

작은 수정은 해당 절과 직접 영향만 확인한다. 책임·구조가 바뀌면 문서 전체와 관련 Owner를 확인한다.

### 8.2 완료 점검

- [ ] 규칙과 상세 근거가 올바른 Owner에 있고 다른 문서에 중복되지 않는가?
- [ ] 첫머리에서 현재 선택을 알 수 있으며 계획·구현·확인 결과를 혼동하지 않는가?
- [ ] 주장 표현이 실제 근거의 범위와 한계에 맞는가?
- [ ] 낡은 내용·중복·완료 항목을 정리하면서 고유 근거·반례·중요 제약은 보존했는가?
- [ ] 영향받는 문서·링크·Metadata·Revision이 현재 상태와 맞는가?

자동 검사는 제목 계층·링크·Metadata 등 형식을 확인하는 데 사용한다. 설계 논리와 근거의 충분성은 개발자가 판단한다. 자동 검사 통과를 설계 효과의 검증으로 기록하지 않는다.

### 8.3 LLM과 도구 사용

현재 설계를 다룰 때 PRJ와 질문의 Owner를 우선 확인하고 필요한 인터페이스 문서만 추가한다. Archive는 과거 비교나 선택 이유가 필요할 때 확인한다. 검색과 Backlinks는 중복 정의와 변경 영향을 찾는 데 사용한다.

LLM은 초안·검색·충돌 탐지를 보조한다. 자료가 없는 규칙·비교 이력·시험·참여자·수치·결과를 만들어 채우지 않는다. 새 정보가 필요하면 확인 필요 또는 작성자 입력이 필요한 부분으로 남긴다. 대화에서 확정한 결정은 Owner의 현재 설명에 반영하고 대화 경위를 복사하지 않는다.
